# Rule Testing

Rule testing has two layers: rulepack validation proves the YAML matches the schema and examples, while integration fixtures prove source-to-sink behavior against real adapter facts.

<Steps>

1. Add or update `match_examples` on every enabled rule.
2. Run rulepack validation.
3. Run match-example collision auditing.
4. Add a fixture when propagation behavior changes.
5. Run the deployment readiness checks that cover the affected command
   surface.

</Steps>

## Match Examples

Positive examples should contain the exact callee or target shape the rule claims. Negative examples should cover the closest safe form, usually a literal argument, disabled option, or wrong receiver.

```yaml
match_examples:
  - name: tainted arg 0
    code: |
      void example(char *input) {
        system(input);
      }
  - name: literal command negative
    code: |
      void example(void) {
        system("echo safe");
      }
    expect_no_match: true
```

## Pack Validation

```bash
cargo build --release -p bonsai_cli
python3 scripts/validate-pattern-pack.py \
  --binary ./target/release/bonsai-ninja \
  --json-out /tmp/pattern-pack-validator.json
```

## Integration Fixtures

Use `examples/<lang>/micro` for small command-surface checks, `mega_flow` for construct coverage, and focused fixtures for sanitizer or lifecycle behavior.

```bash
./target/release/bonsai-ninja security examples/python/mega_flow taint-analysis \
  --rules-dir security-patterns \
  --format json \
  --all
```

## Large-Codebase Performance Checks

For large Java or JVM-family repositories, validate both cold and warm runs.
Keep the real codebase in `/tmp`, delete it after the audit, and run the
release binary with progress disabled for machine-readable logs:

```bash
env BONSAI_DEBUG=security-phase,idg-build \
  ./target/release/bonsai-ninja security /tmp/large-java-project taint-analysis \
  --profile production \
  --format json \
  --no-color \
  --no-progress > /tmp/bonsai-large-java-taint.json
```

The 2026-06-03 Elasticsearch smoke covered 29,839 JVM-family source files and
completed cold in 419.48s, then warm in 215.49s with byte-identical JSON. The
warm run loaded the deterministic transfer sidecar key and avoided rebuilding
the 3.1 GiB chunked IDG factstore. A valid large-codebase run should have
`analysis_complete: true`, no incomplete reasons, no malformed page metadata,
no `payload exceeds 4GiB` warning, and no `save_to_disk failed` warning.

## Security Pattern Audit

Use this stricter pass when reviewing the checked-in rulepack end to end:

```bash
./target/release/bonsai-ninja security . pack --validate \
  --format json \
  --no-color \
  --no-progress

./target/release/bonsai-ninja security . pack --audit \
  --format json \
  --no-color \
  --no-progress

python3 scripts/pack_audit.py --duplicates --fail-on-family-file-mismatch
python3 scripts/pack_audit.py --json > /tmp/bonsai-pack-audit.json

cargo test -p bonsai_security --test rulepack_conformance -- --test-threads=1
cargo test -p bonsai_security --test false_positive_guards -- --nocapture
cargo test -p bonsai_security --test validate_pack_constraint_coverage -- --nocapture
cargo test -p bonsai_security --test validate_pack_negative_examples -- --nocapture
cargo test -p bonsai_security --test pack_constraint_coverage_property -- --nocapture
cargo test -p bonsai_security --test vuln_class_regression -- --nocapture
cargo test -p bonsai_cli --test sanitizer_fixtures -- --nocapture
```

For the audit to be clean, `pack --validate` must report zero warnings and
errors, `pack --audit` must have no unexplained canonical family gaps, and
`pack_audit.py` must report zero duplicate ids, zero duplicate enabled match
shapes, zero cross-family API collisions, zero family-file mismatches, zero
unreviewed fragile bare-name rules, and no unresolved canonical sink-family
gaps. The intentional exceptions are the same as the CLI audit: Solidity uses
an ecosystem-specific taxonomy, and C deserialization is not applicable.

`cargo test --workspace --no-fail-fast` is the broad local sweep used for
release-confidence runs. It is much slower than the focused deployment pass
because it builds and runs every debug test target, including integration
matrices, inspect matrices, cache/hot-reload tests, SARIF tests, doc tests, and
21-language command/content suites. Run it periodically before a release branch
or overnight validation; after scoped rulepack, formatter, or command-output
changes, the focused checks above cover schema validity, SARIF shape,
21-language mega-flow behavior, sanitizer fixtures, and the release CLI command
surface.

No Rust test-startup caveat remains open from the 2026-06-03 deployment pass.
The earlier `_dyld_start` stalls on the local macOS host were fixed by cleaning
an overgrown generated `target/` tree; fresh default-target test harnesses then
launched normally, and `cargo test --workspace --no-fail-fast -- --test-threads=1`
completed successfully. If a future test parent appears idle,
inspect child processes before treating it as a Rust harness hang; some harnesses
legitimately wait on child scripts such as `scripts/validate-mega-cli.py`.
