# Rule Testing

Rule testing has two layers: rulepack validation proves the YAML matches the schema and examples, while integration fixtures prove source-to-sink behavior against real adapter facts.

<Steps>

1. Add or update `match_examples` on every enabled rule.
2. Run rulepack validation.
3. Run match-example collision auditing.
4. Add a fixture when propagation behavior changes.
5. Run the deployment readiness checks that cover the affected command
   surface.

</Steps>

## Match Examples

Positive examples should contain the exact callee or target shape the rule claims. Negative examples should cover the closest safe form, usually a literal argument, disabled option, or wrong receiver.

```yaml
match_examples:
  - name: tainted arg 0
    code: |
      void example(char *input) {
        system(input);
      }
  - name: literal command negative
    code: |
      void example(void) {
        system("echo safe");
      }
    expect_no_match: true
```

## Pack Validation

```bash
cargo build --release -p bonsai_cli
python3 scripts/validate-pattern-pack.py \
  --binary ./target/release/bonsai-ninja \
  --json-out /tmp/pattern-pack-validator.json
```

`pack --validate` checks schema, required metadata, and statically replays
each rule's `match_examples` against the matcher. By default it cannot
replay **taint-dependent** rules (`arg_tainted` / `any_arg_tainted` /
`receiver_tainted`) — those need live source-to-sink dataflow, so the
static pass skips them.

Add `--taint-replay` for the deep gate: it seeds each taint-dependent
rule's positive example through live taint analysis (treating inferred
inputs as sources) and reports any rule whose own example no longer fires
as `match-example-taint-miss`. This catches a rule that silently stopped
matching after a gate, receiver-name, or arg-index change. It runs taint
per example, so it is slower than the default — intended for the deep CI
gate rather than every edit.

```bash
./target/release/bonsai-ninja security . pack --validate --taint-replay \
  --rules-dir security-patterns \
  --format json --no-color --no-progress
```

A `match-example-taint-miss` usually means one of: the rule is genuinely
broken; its package gate rejects the receiver (give the rule a
`receiver_type_in` constraint and construct the receiver in the example —
see [Pattern Guide](pattern-guide)); or the example uses a literal instead
of a function-parameter source, so there is nothing to taint.

## Integration Fixtures

Use `examples/<lang>/micro` for small command-surface checks, `mega_flow` for construct coverage, and focused fixtures for sanitizer or lifecycle behavior.

```bash
./target/release/bonsai-ninja security examples/python/mega_flow taint-analysis \
  --rules-dir security-patterns \
  --format json \
  --all
```

## Large-Codebase Performance Checks

For large Java or JVM-family repositories, validate both cold and warm runs.
Keep the real codebase in `/tmp`, delete it after the audit, and run the
release binary with progress disabled for machine-readable logs:

```bash
env BONSAI_DEBUG=security-phase,idg-build \
  ./target/release/bonsai-ninja security /tmp/large-java-project taint-analysis \
  --profile production \
  --format json \
  --no-color \
  --no-progress > /tmp/bonsai-large-java-taint.json
```

The 2026-06-06 Elasticsearch smoke used the reported CLI shape,
`security ../elasticsearch taint-analysis --context 512k --no-color
--no-progress`, against the local Elasticsearch checkout. The release run
completed in 121.25s with 327 total findings and no `payload exceeds 4GiB` or
`save_to_disk failed` warning. Phase timing with
`BONSAI_DEBUG=security-phase` showed source matching in 6.776s, sink matching
in 5.200s, sanitizer matching in 4.685s, source-reachable callgraph
construction in 11.968s, scoped semantic graph construction in 6.939s,
source-sink reachability in 0.004s, taint-chain building in 23.262s, flow
evidence in 0.012s, and first-page rendering in 1.011s. The source-reachable
graph was scoped to 15,557 functions / 3,074 files from 2,018 source functions
and 7,954 sink functions, reaching 1,745 sink functions; the IDG scope was
further narrowed to 13,876 functions / 2,958 files. Source groups were filtered
from 2,018 to 497.

A valid large-codebase run should have `analysis_complete: true` for JSON/SARIF
runs, no incomplete reasons, no malformed page metadata, no `payload exceeds
4GiB` warning, and no `save_to_disk failed` warning. Large Java scopes should
log `large_java_scope=true`, `receiver_method_propagation=false`, and
`field_argument_forwarding=false` in the scoped semantic graph phase; exact
taint still runs over source-to-sink IDG/callgraph corridors rather than a
workspace-wide graph.

`BONSAI_DEBUG=security-phase` writes phase timing to stderr even when
`--no-progress` keeps stdout clean. `--no-progress` and `NO_PROGRESS` are the
only progress mute switches; `--no-color` and `NO_COLOR` keep progress visible
in an interactive terminal but render monochrome bars. For taint-analysis,
expect separate progress phases and timings for rule loading, parsing,
source/sink/sanitizer matching, semantic graph construction, source-sink
reachability, taint scheduling, taint-chain building, finding finalization,
flow evidence, and JSON/text rendering. Text output also reports page cost
estimation, pagination, page-window rendering, and page-cache save time.
The rendered page cache reuses the indexed source fingerprint from the opened
workspace, so a first-page render should not perform a second full source-tree
content scan after analysis completes.
Rendered-page caching is intentionally opportunistic: it renders the first four
pages plus the current page and up to the next three pages. This keeps
`--page 2` cheap without making large source-body reports wait for dozens of
future pages to render before stdout is returned.

Add `idg-build` when a run is slow after rule matching. That expands the
semantic graph phase into map construction, transfer, call-name aliases,
call-edge site indexing, IDG stitching, field forwarding, and receiver
propagation. For package-oriented languages, call-edge site counts should stay
proportional to real call sites. A sibling-package same-name explosion means
module/package narrowing regressed.

The summary-output corridor is intentionally source-origin scoped. It can climb
return-to-caller edges from a source-bearing helper when the helper has a
semantic output summary, then continue through the caller-to-callee graph. That
keeps returned-object flows schedulable without letting every reached
summary-returning utility fan out to unrelated callers.

The 2026-06-04 and 2026-06-06 source-to-sink scheduler regression passes verify
that taint-analysis does not analyze every source in a large project when most
sources cannot reach any sink. Source eligibility is source-scoped: the
scheduler uses concrete source-seed to sink-node IDG cuts when possible, uses a
source-origin resolved-callgraph corridor when a concrete node cut cannot prove
completeness, and skips source groups with no semantic source-to-sink corridor.
It must not materialize all semantic function edges before source filtering,
the taint budget must not cap source eligibility, and there is no workspace-wide
graph fallback. Once a source group is eligible, the per-source IDG graph build
is cut to the proven source-to-sink corridor. Same-file source batches also get
a concrete seed-node to sink-node reachability prefilter so adapter module
wrappers or dense files do not schedule source-only calls. Cross-file node-cut
uncertainty stays scheduled and is decided by the normal corridor-scoped
semantic taint graph to avoid false negatives.

## Security Pattern Audit

Use this stricter pass when reviewing the checked-in rulepack end to end:

```bash
./target/release/bonsai-ninja security . pack --validate \
  --format json \
  --no-color \
  --no-progress

./target/release/bonsai-ninja security . pack --audit \
  --format json \
  --no-color \
  --no-progress

python3 scripts/pack_audit.py --duplicates --fail-on-family-file-mismatch
python3 scripts/pack_audit.py --json > /tmp/bonsai-pack-audit.json

cargo test -p bonsai_security --test rulepack_conformance -- --test-threads=1
cargo test -p bonsai_security --test false_positive_guards -- --nocapture
cargo test -p bonsai_security --test validate_pack_constraint_coverage -- --nocapture
cargo test -p bonsai_security --test validate_pack_negative_examples -- --nocapture
cargo test -p bonsai_security --test pack_constraint_coverage_property -- --nocapture
cargo test -p bonsai_security --test vuln_class_regression -- --nocapture
cargo test -p bonsai_cli --test sanitizer_fixtures -- --nocapture
```

For the audit to be clean, `pack --validate` must report zero warnings and
errors, `pack --audit` must have no unexplained canonical family gaps, and
`pack_audit.py` must report zero duplicate ids, zero duplicate enabled match
shapes, zero cross-family API collisions, zero family-file mismatches, zero
unreviewed fragile bare-name rules, and no unresolved canonical sink-family
gaps. The intentional exceptions are the same as the CLI audit: Solidity uses
an ecosystem-specific taxonomy, and C deserialization is not applicable.

`cargo test --workspace --no-fail-fast` is the broad local sweep used for
release-confidence runs. It is much slower than the focused deployment pass
because it builds and runs every debug test target, including integration
matrices, inspect matrices, cache/hot-reload tests, SARIF tests, doc tests, and
21-language command/content suites. Run it periodically before a release branch
or overnight validation; after scoped rulepack, formatter, or command-output
changes, the focused checks above cover schema validity, SARIF shape,
21-language mega-flow behavior, sanitizer fixtures, and the release CLI command
surface.

No Rust test-startup caveat remains open from the 2026-06-03 deployment pass.
The earlier `_dyld_start` stalls on the local macOS host were fixed by cleaning
an overgrown generated `target/` tree; fresh default-target test harnesses then
launched normally, and `cargo test --workspace --no-fail-fast -- --test-threads=1`
completed successfully. If a future test parent appears idle,
inspect child processes before treating it as a Rust harness hang; some harnesses
legitimately wait on child scripts such as `scripts/validate-mega-cli.py`.
