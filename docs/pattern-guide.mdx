# Pattern guide

How to author rules for the bonsai-ninja security rulepack. The validator
enforces these contracts at load time; rules that fail validation are
rejected.

## File layout

```
security-patterns/langs/<lang>/{sources,sinks,sanitizers}/<family>.yml
```

The directory determines the rule kind. `<lang>` matches one of the 21
supported language IDs. `<family>` is a free-form filename that groups
related rules - `cmdi.yml`, `sqli.yml`, `xss.yml`, etc.

## Minimum viable rule

```yaml
- id: python.cmdi.os_system
  enabled: true
  language: python
  tag: command-injection
  severity: critical
  packages: [os]
  imports: [os]
  cwe: [CWE-78]
  match:
    kind: call
    callee:
      attribute: [os, system]
  constraints:
    - arg_tainted: { index: 0 }
  match_examples:
    - name: os.system call
      code: |
        import os
        def example(user):
            os.system(user)
      expect_match_text: [os.system]
  description: "os.system(cmd) - tainted shell command execution."
```

Required:

- `id` - unique per (language, kind).
- `language` - required in flat layout, optional in canonical layout.
- `match.kind` - `call`, `new`, `read`, `write`, `return`, or `param`.
- `match.callee` (call/new) or `match.target` (read/write/return/param).
- `description` - at least 15 chars; explains the API shape and the
  security consequence.
- `match_examples` - at least one entry with `code` that fires the rule.

Sinks also need `cwe` and `severity`. Sources need `trust`.

## Match shapes

`kind:` selects what the rule matches:

| `kind` | Matches | Target field |
|---------|---------|--------------|
| `call` | a function / method call | `callee` |
| `new` | a constructor call (`new T(...)` or `T(...)`) | `callee` |
| `read` | a container / attribute read (source side) | `target` |
| `write` | a container / attribute write (sink side) | `target` |
| `return` | a function's return expression | `callee` |
| `param` | a declaration's parameter identifier | `target` |
| `missing` | fires when the target call is ABSENT on a path (see the walker section) | `target` |

**Attribute path** - preferred for `Type.method` calls:

```yaml
match:
  kind: call
  callee:
    attribute: [requests, get]
```

The matcher's alias map handles `from requests import get as r; r(...)`
automatically.

**Bare name** - use sparingly, pair with `packages:` to narrow:

```yaml
match:
  kind: call
  callee:
    name: open
```

**Regex** - for variable receivers with a distinctive verb:

```yaml
match:
  kind: call
  callee:
    regex: "^[A-Za-z_$][A-Za-z0-9_$]*\\.body$"
```

Receiver-agnostic regexes **must** declare `packages:`, `imports:`, or
`modules:` so the matcher can require adapter-visible file context before
the regex is considered.

When a receiver-agnostic regex still needs exact local receiver names,
add `base_name_in` instead of hardcoding the receiver into the regex:

```yaml
match:
  kind: read
  target:
    regex: "^[A-Za-z_$][A-Za-z0-9_$]*\\.[A-Za-z_$][A-Za-z0-9_$]*$"
    base_name_in: [args, variables]
```

This is the preferred shape for contextual resolver maps such as GraphQL
`args.<field>`: it allows arbitrary field names while keeping sibling
objects like `user.id` clean.

**Annotation / decorator** - Spring `@RequestParam`, FastAPI binders,
etc.:

```yaml
match:
  kind: param
  target:
    annotation: RequestParam
```

Reads `Decl.param_annotations`.

**Read / write target** - for source-side container reads:

```yaml
match:
  kind: read
  target:
    attribute: [request, body]
```

The matcher walks `Assign.source_names` against this shape.

## Constraints

`constraints` is a list of small, composable predicates that run after the
match shape fires.

### `arg_tainted`

```yaml
constraints:
  - arg_tainted: { index: 0 }     # positional
  - arg_tainted: { kw: data }     # keyword
```

Defers to the engine's per-site taint verdict for the vulnerable operand.
For `match.kind: call` and `new`, `index` is the syntactic call argument
index. For `match.kind: write`, `index: 0` is the assignment RHS, so write
sinks such as `obj.innerHTML = value` or `settings.CommandText = value`
can stay declarative in YAML without engine hardcoding. Sink rules anchored
on `arg_tainted` only fire when the engine can prove that selected operand
flows from a source.

Do not use `arg_tainted` for source-independent configuration findings
such as template autoescape disabled, Angular resource whitelist wildcards,
or parser entity-processing flags. Those rules are local API/config misuse
patterns, not source-to-sink claims. `match.kind: return` rules also do not
have call arguments; their taint gate is return-expression reachability.

### `receiver_tainted`

```yaml
constraints:
  - receiver_tainted: true
```

Use this when the vulnerable operand is the call receiver rather than a
syntactic argument. Examples include Scala `cmd.!`, Solidity
`target.delegatecall("")`, and fluent APIs where the dangerous value sits
to the left of the method call. Do not model these as `arg_tainted`;
zero-argument receiver calls have no argument slot to prove.

### `any_arg_tainted`

```yaml
constraints:
  - any_arg_tainted: true
```

Use this only when the API treats every syntactic argument as the same
dangerous payload surface, such as variadic command fragments or generic
message/body forwarding calls. Prefer `arg_tainted` for APIs where one
operand has a specific security meaning (`eval(expr, globals)`,
`memcpy(dst, src, n)`, redirect target, SQL query text, length/count
arguments, and similar fixed-slot shapes). `any_arg_tainted` still
requires a real taint verdict on at least one call argument; literal-only
calls and zero-argument calls do not match.

For write rules, prefer `arg_tainted: { index: 0 }` when the assignment is
only dangerous with attacker-controlled data. This prevents sibling taint in
the same function from turning literal/config writes into false source-to-
sink flows.

For bounded-copy rules, constrain the *bound* argument, not just the
pointers. C/C++ `memcpy(dst, src, n)` uses `index: 2`. A fixed constant
like `FIXED_LEN` is not evidence of CWE-120 just because `dst` or `src` is
tainted.

Allocation rules follow the same rule - pin the size/count operand:
`malloc(n)` index 0, `realloc(ptr, n)` index 1, `aligned_alloc(align,
size)` index 1, `calloc(nmemb, size)` needs a rule for each.

### `arg_equals` / `keyword_arg_equals`

```yaml
- arg_equals: { index: 1, value: "shell=True" }
- keyword_arg_equals: { name: "shell", value: "True" }
```

### `arg_matches_regex` / `arg_not_matches_regex`

```yaml
- arg_matches_regex: { index: 0, regex: "^/api/" }
- arg_not_matches_regex: { index: 0, regex: "\\+|fmt\\.Sprintf" }
```

`arg_not_matches_regex` is the negation - the match holds only when arg N
does NOT match. Useful to exclude already-escaped or constant-built
arguments (e.g. a query assembled with `+` concatenation).

### `any_arg_matches_regex`

```yaml
- any_arg_matches_regex: |-
    HttpOnly.*true|Secure.*true
```

Matches when ANY argument matches the regex, regardless of position - for
varargs / option-bag sinks where the relevant flag can land in any slot.

### `receiver_type_in`

```yaml
- receiver_type_in: [HttpClient]
```

`receiver_type_in` is derived from adapter-emitted type facts, not from
local variable names. Those facts come from typed parameters and fields
(`def handle(conn: Connection)`), class-field bindings, and — for
dynamically-typed languages — **local constructor assignments**
(`conn = ldap3.Connection(server)` types `conn` as `Connection`). So the
preferred shape for a receiver-specific sink on a dynamic API is a
receiver-agnostic callee regex **plus** a `receiver_type_in` constraint:
the type constraint resolves the receiver by structure and keeps the rule
precise without leaning on the package gate alone. Write the rule's
`match_examples` so they *construct* the receiver, otherwise the type
fact (and the match) won't be there.

When the receiver genuinely cannot be typed (an untyped parameter with no
constructor in scope), fall back to a receiver-agnostic regex plus
adapter-visible `packages:` / `imports:` / `modules:` signals and
taint/argument constraints — but expect lower precision than a
`receiver_type_in` rule.

### `format_arg_index`

```yaml
- format_arg_index: 0
```

Treats arg N as a format string - for `printf`-shaped sinks.

### `top_level`

```yaml
- top_level: true     # match must be at module top-level
- top_level: false    # match must NOT be at module top-level
```

`true` requires the match to sit at module top-level; `false` requires it
to be nested (inside a function/class). Distinguishes a top-level
`yaml.load(...)` from a method decoy like `obj.Load(...)`.

### `in_class` / `in_method` / `decl_kind_in` / `visibility_in`

```yaml
match:
  kind: param
  target:
    name: payload
    in_class: WebSocketHandler
    decl_kind_in: [method]
    visibility_in: [public]
```

`in_class` consults `Decl.parent` and `Decl.bases`, so subclasses match
their declared parent. `decl_kind_in` and `visibility_in` use
adapter-emitted declaration metadata, which lets param rules distinguish
public entrypoint methods from internal helpers, constructors, modifiers,
or other function-shaped declarations without hardcoding language APIs in
the engine.

### `arg_count` / `max_args` / `min_args`

```yaml
- arg_count: 1     # exactly one argument
- max_args: 3      # at most three
- min_args: 2      # at least two
```

Argcount bounds. `arg_count` pins an exact arity (disambiguates a 1-arg
`localStorage.getItem` read from multi-arg overloads); `max_args` /
`min_args` bound a range. Useful when overload disambiguation matters.

### `same_receiver_call_count_at_least`

```yaml
- same_receiver_call_count_at_least: 2
```

Holds when the same receiver is the target of at least N calls in scope -
e.g. a paired same-origin guard where one call sets and another checks the
same object, so a lone unguarded call still fires.

### `arg_lt` / `arg_le` / `arg_gt` / `arg_ge`

```yaml
- arg_lt: { index: 0, value: 2048 }    # weak crypto strength
- arg_ge: { index: 1, value: 31536000 } # session timeout > 1y
```

Integer-literal comparison. Decimal / hex / oct / bin / underscore
forms are accepted. Non-literal args (variables, expressions) fail
the constraint conservatively.

### `requires_runtime_type`

```yaml
- requires_runtime_type: { index: 0, type: TrustedShape }
```

The arg at `index` must be narrowed to the declared type by a
preceding type-test guard inside the same decl: `instanceof X`,
`isinstance(_, X)`, `_ is X`, or `typeof _ === "X"`. The narrowing
is CFG-aware - only the then-branch of the guard counts; outside
that range the constraint fails closed.

### `enclosing_decorator_in`

```yaml
- enclosing_decorator_in: [route, post, get]
```

The enclosing decl must carry a decorator / annotation whose tail
matches one of the listed names. Useful for scoping `kind: missing`
rules to handler decls (`@app.route`) without firing on every
helper. Splits dotted decorator names so `@app.route` matches
both `route` and `app`.

### `must_alias`

```yaml
- must_alias: { source_arg: 0, sink_arg: 1 }
```

The source and sink args at this call site must share a must-alias
root within the same decl. Same name on both sides is the trivial
must-alias; rename chains (`y = x; pair(x, y)`) propagate.
Compound RHS (`y = f(x)`, `y = x + 1`) is not aliasing.

### `requires_state`

```yaml
- requires_state: { name: fd, expected: closed }
```

The named binding must be in `expected` lifecycle state at the
call site. Adapters emit `FlowEvent::Lifecycle` events on
recognised free / close / unlock / cancel / move / dispose calls
(see `kit::inject_lifecycle_events`); the matcher's flow-sensitive
lattice picks up the most recent transition before the call.
Canonical states: `freed`, `closed`, `unlocked`, `cancelled`,
`moved`. Used by audit-pair UAF / use-after-close rules to gate
findings on actual transition correlation rather than firing on
the transition site alone.

## Source Output Arguments

Use `taint_semantics.source_output_args` for source APIs that write
untrusted data into caller-owned output arguments instead of returning
the untrusted value.

```yaml
- id: c.input.recv
  enabled: true
  language: c
  trust: remote
  tag: network-input
  match:
    kind: call
    callee:
      name: recv
  taint_semantics:
    source_output_args: [1]
  description: "recv(fd, buf, len, flags) - remote bytes taint buf."
```

This is the right model for `recv`, `recvfrom`, `SSL_read`, `fgets`,
FreeRTOS receive APIs, serial/SPI reads, and similar out-buffer calls.
Do not model these as ordinary call sources without
`source_output_args`; that would also taint descriptors, lengths, flags,
and handles.

## Output Argument Flows

Use `taint_semantics.output_arg_flows` for APIs that copy or format
value-bearing inputs into a caller-owned output argument. This is a
transfer fact, not a source by itself: it only fires when one of the
configured value inputs is already tainted.

```yaml
- id: c.format.sprintf_tainted
  enabled: true
  language: c
  tag: format-string
  match:
    kind: call
    callee:
      name: sprintf
  constraints:
  - arg_tainted:
      index: 1
  taint_semantics:
    output_arg_flows:
    - output_arg_index: 0
      value_start_arg_index: 1
  description: "sprintf(buf, fmt, ...) writes formatted tainted data into buf."
```

Use `value_start_arg_index` for varargs shapes where every argument from
that index can contribute to the output, and `value_arg_indices` for
fixed input positions. Do not add formatter/copy behavior to engine code:
different libraries use different argument order and overwrite semantics,
so those facts belong in editable rules.

## Clean Output Overwrites

Use `taint_semantics.clean_output_overwrite` for APIs that overwrite an
output argument with freshly produced data. Clean configured inputs kill
stale taint on the output; tainted configured inputs still flow into the
output. This models calls like bounded formatters without making them
global sanitizers for every use.

```yaml
- id: c.sanitizer.snprintf_bounded
  enabled: true
  language: c
  tag: validation
  match:
    kind: call
    callee:
      name: snprintf
  taint_semantics:
    clean_output_overwrite:
      output_arg_index: 0
      value_start_arg_index: 2
  description: "snprintf overwrites buf with formatted value inputs."
```

Keep overwrite argument order in YAML. Do not special-case formatter or
buffer APIs in the engine; the graph only applies the generic transfer
primitive declared by the rule.

## Call-Result Passthroughs

Use `taint_semantics.call_result_passthrough_args` for APIs that change
representation but do not remove attacker control. This is common for URL
decoders, HTML entity decoders, base64 decoders, string/byte splitting,
and similar helpers: `decoded = decode(input)` or
`parts = strings.Fields(input)` should preserve taint from `input`, but
the engine must not hardcode every library method.

```yaml
- id: java.passthrough.urldecoder_decode
  enabled: true
  language: java
  tag: passthrough-decode
  match:
    kind: call
    callee:
      attribute: [URLDecoder, decode]
  taint_semantics:
    call_result_passthrough_args: [0]
  description: "URLDecoder.decode(s, charset) preserves taint from s."
```

Keep these as sanitizer/passthrough rules with a non-crediting tag such
as `passthrough-decode` or `passthrough-transform`; they are transfer
facts, not evidence that a sink has been sanitized. Do not replace this
with a generic engine heuristic, because unrelated application methods
with similar names may validate, ignore, or transform different operands.
The matcher normalizes common qualified-name separators (`.`, `::`, `->`,
and Erlang `:`), so structured callee attributes can represent language
surface syntax without hardcoding that API in Rust code.

Formatter constructors and builders are passthrough transforms when the
returned value is composed from later arguments. Keep the contributing
argument slots in the rulepack, for example Objective-C
`NSString.stringWithFormat` preserves taint from its formatted value
arguments with `call_result_passthrough_args: [1, 2, 3, 4, 5]`. The rule
should carry a passthrough tag such as `passthrough-transform` so it
extends flow without granting sanitizer clearance.

For receiver-return transforms, use
`taint_semantics.call_result_passthrough_receiver: true` instead of a
sentinel argument index:

```yaml
- id: swift.passthrough.removing_percent_encoding
  enabled: true
  language: swift
  tag: passthrough-decode
  match:
    kind: call
    callee:
      name: removingPercentEncoding
  taint_semantics:
    call_result_passthrough_receiver: true
  description: "value.removingPercentEncoding preserves taint from value."
```

## Receiver-State Mutators

Use `taint_semantics.taint_receiver_from_args: true` when a tainted
argument mutates the receiver and a later receiver-only sink consumes that
state.

```yaml
- id: java.sqli.statement_executebatch
  enabled: true
  language: java
  tag: sql-injection
  match:
    kind: call
    callee:
      attribute: [Statement, addBatch]
  constraints:
    - arg_tainted: { index: 0 }
  taint_semantics:
    taint_receiver_from_args: true
```

Pair it with a later sink such as `Statement.executeBatch` using
`receiver_tainted: true`. The engine derives the receiver type and method
from the structured callee target; there is no global list of mutator
method names.

## `kind: missing` walker

```yaml
match:
  kind: missing
  callee:
    attribute: [csrf, validate]
  search_depth: 0   # default: intra-procedural only
constraints:
  - enclosing_decorator_in: [route, post, get]
```

Inverse-match: fires on every function-shaped decl that does
*not* contain a call to the declared target. `search_depth > 0`
extends the walker to BFS through resolved callees up to that
depth (capped at 4 engine-side); use sparingly - cheaper to keep
the walker intra-procedural and add scoping via
`enclosing_decorator_in` or package gates.

## Subsumption / disabling

Disabled rules must declare a reason:

```yaml
- id: python.deprecated.foo
  enabled: false
  disabled_reason:
    code: subsumed
    subsumed_by: python.canonical.foo
```

`code` is one of:

- `subsumed` - covered by another (more general) rule. Requires
  `subsumed_by`.
- `over-broad` - original pattern was too permissive.
- `requires-constraint` - needs an extra constraint arm to fire cleanly.
- `pending-adapter-fact` - needs an adapter capability not yet exposed.

The `subsumed_by` chain must terminate at an enabled rule.

## Merged Families And Aliases

Use `aliases` when one enabled rule intentionally covers another historical
rule id or a second vulnerability family without duplicating the same API
shape:

```yaml
- id: lua.path.io_open_read
  aliases:
    - lua.upload_io_open_client_filename
  enabled: true
  tag: path-traversal
  cwe: [CWE-22, CWE-434]
```

Aliases count as coverage in `security pack --audit`, so a path write rule
that also covers a client-supplied upload filename can satisfy both `path`
and `file_upload` audit cells. Keep the primary `id` in the file that owns
the canonical match shape, and keep the alias only when it preserves a real
security-family attribution. Do not duplicate enabled rules with identical
match/constraint shapes just to fill a second audit column.

## Receiver Context

Structured `attribute:` rules are strict. `[Eta, render]` matches exact
module/static calls such as `Eta.render(...)`; instance calls such as
`engine.render(...)` require adapter-emitted receiver-type facts that prove
`engine` is an `Eta`.

```yaml
packages: [eta]
imports: [eta]
match:
  kind: call
  callee:
    attribute: [Eta, render]
```

When an API is commonly imported under arbitrary local aliases, write an
explicit receiver-agnostic regex and gate it with adapter-visible
package/import/module signals. Do not rely on a specific local variable name
to identify an API.

## Match examples

Every rule must include at least one `match_examples` entry:

```yaml
match_examples:
  - name: os.system call
    code: |
      import os
      def example(user):
          os.system(user)
    expect_match_text: [os.system]
```

The `code` is parsed and matched at validation time - if the rule wouldn't
fire on its own example, validation rejects it. Add multiple examples for
notable variant shapes; see [Pattern Variants](pattern-variants.mdx) for common
variants worth covering.

## Severity

Sinks need `severity`: `critical`, `high`, `medium`, `low`, or `info`.
The CLI ranks findings by severity; SARIF maps it to GitHub's
high/error/warning levels.

## CWE mapping

`cwe: [CWE-78, CWE-77]` - multiple are fine. The first listed CWE drives
SARIF tag selection.

## Validation tips

Run `bonsai-ninja security pack --validate path/` to lint a rulepack
locally. Add `--audit` for the coverage matrix. The validator catches
missing examples, broken `subsumed_by` chains, severity/CWE typos, and
match shapes that wouldn't fire on their own examples.
