# CLI Reference

Global options accepted before or after the command include `--no-color`,
`--theme`, `--no-cache`, `--no-progress`, `--html-output`, `--contains`,
`--not-contains`, `--parse-timeout`, `--memory-budget`, `--minified-js`,
`--debug`, `--help`, and `--version`. `--memory-budget <MIB>` controls exact compiler-work
scheduling and spill/retention policy; it never caps files, graph depth,
fixed-point iterations, or results. `--debug <CATEGORIES>` emits selected
diagnostic categories to stderr and is equivalent to `BONSAI_DEBUG`.
`--theme` and `BONSAI_THEME` accept exactly `moss`, `earthy-dark`,
`dracula`, or `retro-amber`; unknown values are errors.

`--contains <TEXT>` (repeatable; every value must match) and
`--not-contains <TEXT>` (repeatable; no value may match) are views over the
command's complete result: they keep the rows whose string fields — the same
fields the JSON `rows[]` entry carries, plus the rendered `file:line[:column]`
location — contain the text, case-insensitively. They never re-run analysis
and never read source lines, enclosing functions, callee summaries, or other
presentation extras derived for the rendered page, so narrowing a large
result costs one serialization per row.

`--no-cache` and `BONSAI_NO_CACHE=1` select one exact cold invocation. The
command does not load or publish reusable compiler-object, callgraph,
dataflow, value-flow, IDG, taint-graph, export, or rendered-page sidecars.
Exact compiler facts may still be memoized in a temporary command-local store
so later phases do not reparse the same source; that store is discarded when
the process exits. Use `cache clear` when the intent is to remove existing
artifacts rather than bypass them.

Compiler-backed commands use one input profile. By default, each language
adapter can classify minified source representations and the JavaScript and
TypeScript adapters exclude `.min.*` / `-min.*` bundles before parsing. This
keeps generated distribution code out of index, navigation, callgraph,
security, and export work. Global `--minified-js` restores those inputs across
all of those commands; cache manifests record the selection and cannot be
reused across profiles. `tree` is a filesystem walk with compiler facts attached and remains
unfiltered. Explicit `read-file` access to a minified source requires the same
switch.

Workspace roots are positional operands. Query-like values have explicit
forms—`--query`, `--symbol`, `--file`, `--from`, `--to`, and `--id`—which are
preferred in scripts and agent workflows. Concise positional selector forms
remain supported for interactive use. Supplying both forms is a parse error;
the CLI never silently chooses one. File outputs accept the canonical
`--output-path <PATH>` spelling plus the standard `-o <PATH>` and
`--output <PATH>` aliases.

Progress bars render to stderr only. Interactive commands show staged
work such as workspace ingest/parse, reduced-workspace file selection,
workspace sidecar/cache checks, query collection, security analysis
phases, pagination/cache writes, and rendering. Payload output on stdout
and files written with
`--output-path` stay free of progress text. Use `--no-progress` or
`NO_PROGRESS=1` for quiet script/LLM runs; use `--no-color` separately to
disable ANSI styling while keeping progress visible.

`index --semantic` runs its process-isolated workers sequentially and gives
the active worker one terminal line. It reports validation plus five numbered
phases: compiler objects, declaration linkage, callgraph, retrieval, and the
dataflow graph plus its IDG query accelerator. Compiler-object,
declaration-linkage, callgraph,
retrieval, and IDG-transfer work show exact completed/total counters, percent,
throughput, ETA, and elapsed time. The IDG worker then names its accelerator,
persistence, and manifest subphases. Operations without an honest semantic
unit count show elapsed time only. Monotone worklists such as a
source-reachable security callgraph add an exact completed-unit counter as
compiler files or persisted relation partitions finish, but still omit
percentage and ETA because the final total is not known up front. The CLI does
not invent percentages for compression, atomic publication, or other
indivisible work.
Plain `index` reports compiler-cache maintenance, the exact source-file read
worklist after discovery, and Tree-sitter object compilation. Security scans
split broad matching into raw-anchor, syntax-header, optional receiver-type,
and exact-body worklists so large candidate planning advances continuously.
Native JSON export counts its two exact compiler-file passes and names compact
graph streams without inventing a row total. Progress is intentionally absent when stderr
is captured or redirected because that is a non-interactive stream; use a
terminal to see live animation.

`--html-output <PATH>` renders the selected command's canonical result — the
same document `--format json` prints — as a self-contained HTML report:
completeness badges, fact lists, tables for flat rows, cards for nested
records, and `<pre>` blocks for source code. The command runs in its JSON
mode under this flag, so the report carries exactly the facts JSON carries
(same selected objects, same filters, same page) and never enables semantic or
security work the command did not request. It contains no scripts or external
assets. It is mutually exclusive with a command's `--output-path`, and it is
not available for `export` (a streamed graph artifact) or `cache clear` /
`cache rebuild` (no report). Use `--format json` or SARIF when a machine will
consume the artifact.

Long security commands expose detailed scope/cache notes through
`AnalysisProgress`. The CLI renders those notes only when progress is
enabled and `BONSAI_DEBUG=security-progress` is set, so normal terminal
output stays clean while debug runs can show the selected file/rule
scope, source/sink match counts, taint-graph cache hit/miss state, and
write-through sidecar persistence. `--no-progress` and `NO_PROGRESS=1`
mute these notes as well as bars. SDK callers receive the same structured
events through the progress callback. Cold scoped-IDG construction reports
its exact selected segment count before it transitions to persistence.
Taint-graph persistence is enabled
by default for repeated-run reuse; set `BONSAI_TAINT_GRAPH_PERSIST=0` to
opt out of the sidecar write-through.

## Help Layout

`bonsai-ninja help`, `bonsai-ninja --help`, and every parse error share one
themed rendering. `help` alone prints the grouped menu, ordered by workflow:
Workspace, Cache, Navigation, Browse, Flow, Security, Debug. `help <command>`
(and nested paths such as `help security taint-analysis`) prints that
command's full reference, byte-for-byte the same text as `<command> --help`.
An unknown command name, a missing required argument, or an unexpected flag
prints a themed `error:` line (with clap's closest-match tip when one exists)
followed by the help of the command the input addressed — the root menu for an
unknown command — and a `bonsai-ninja help <command>` hint, on stderr with exit
code 2.

`bonsai-ninja --help` is ordered for scanning: intro, `USAGE`,
`COMMAND GROUPS`, `OPTIONS`, `EXAMPLES`, then `SEE ALSO`. Leaf help prints the
full invocation path (including `security <WORKSPACE>` and `cache`) and groups
inherited switches under `GLOBAL OPTIONS`. Root help puts
the grouped command index before global options so users can find the
right command first. All help section headings use uppercase casing
(`USAGE`, `COMMAND GROUPS`, `OPTIONS`, `ARGUMENTS`, `COMMANDS`,
`EXAMPLES`, `SEE ALSO`) for a consistent themed layout across root and
subcommand help.

## index

`index` parses a workspace, builds the syntax/construct index, and prints a
cache summary plus the workspace semantic context. Default/structural mode
reports file, compiler-object, and parse-reuse counts, and a `context` object
with the language-neutral workspace-shape facts the engine uses: indexed
module roots, dependency roots, generated or excluded roots, toolchain
manifests, configured-source hints, source-transformation evidence, and the
reasons the context is incomplete. The SDK exposes the same structure through
`Project::semantic_context()`. `--semantic` reports the same workspace file count plus
whether the complete semantic generation was reused or rebuilt, manifest
freshness, semantic readiness, total cache bytes, and every ready sidecar. A
warm semantic run still prints this summary; successful commands never return
silent output. Whole-workspace semantic sidecars are not warmed unless an
explicit prewarm flag is passed.

```bash
bonsai-ninja index ./src
bonsai-ninja index ./src --watch
bonsai-ninja index ./src --semantic
bonsai-ninja index ./src --structural-only
bonsai-ninja index ./src --prewarm-dataflow
bonsai-ninja index ./src --semantic --minified-js
```

| Flag | Default | Description |
|---|---:|---|
| `<WORKSPACE>` | Required | Workspace root to analyze. |
| `--semantic` | false | Explicitly build and persist the immutable compiler-object generation, resolved callgraph, compiler linkage, retrieval factstore, streamed workspace IDG, and external-cache `manifest.json`. This does not run all-entry dataflow prewarm. |
| `--structural-only` | false | Explicit spelling for default syntax/construct indexing; do not warm reusable semantic sidecars. |
| `--prewarm-dataflow` | false | Compute and persist the compatibility dataflow projection used by older SDK/query surfaces. This does not select another taint engine and can be expensive on large workspaces. |
| `--watch` | false | Keep running, poll the source tree, hot-reload saved changes into the live workspace, and print fresh stats. |
| `--interval-ms <N>` | 750 | Poll interval for `--watch`. Values below 100 ms are clamped to 100 ms. |
| `--format <FORMAT>` | text | `text` for the themed summary or `json` for the complete canonical object. |
| `--output-path <PATH>` | stdout | Write the selected `--format` output to a file. |

Normal `index` runs are syntax index-up-front: later browse, `inspect-graph`,
security, export, and debug commands load reusable sidecars when present and
compute any missing exact analysis scope they need before rendering. Retrieval
sidecars accelerate candidate lookup only; canonical facts and semantic graph
verification still decide truth. Search and literal-filtered browse commands
reuse fresh retrieval sidecars after validating source/dependency/build
fingerprints, and search may build one on demand only for small complete
workspaces. Large-workspace `inspect-graph` can use a warmed sidecar only to choose a
pre-open candidate file scope; once the workspace is open, `inspect-graph` hydrates
from canonical syntax and graph facts. Large/scoped query workspaces fall back
to canonical syntax-backed collection when the sidecar is absent or stale
instead of writing partial retrieval state into the complete workspace cache. Use `--semantic` only
when a workflow deliberately wants to front-load the full semantic sidecar cost.

On a warm default run, `index` validates the compiler generation from its
root-only source fingerprint ledger and reads workspace context from file
metadata. It does not reopen every source body merely to print cache counters.
An absent or stale generation takes the exact cold path: source files are
ingested, lowered through their Tree-sitter adapters, and republished as one
complete immutable compiler-object generation.

Semantic prewarm uses ordered process phases: compiler objects, callgraph,
retrieval, linkage, then IDG/manifest. The first phase lowers each immutable
source snapshot once; later phases stream those objects. IDG transfer lowering
also runs once: a bounded source-weighted worker window lowers independent
segments ahead of the stitcher, and a reorder buffer publishes only canonical
segment order before replaying the compact typed stitch spool. Process exits
reclaim phase arenas, and file-size-weighted scheduling subtracts current
process RSS and safety headroom from detected memory before adapting
concurrency, without capping semantic work. A 3 GiB process budget may
serialize large transient units while allowing small units to overlap. The
workspace linker keeps only compact declaration/type/module headers and stable
symbols; consumers stream exact bodies and remap them to those symbols.
Repeated exact-body consumers share a byte-weighted hot cache derived from the
same memory budget; eviction causes exact recomputation, not missing files or
facts. After the IDG worker, the parent validates
that every artifact describes the same workspace snapshot; an intervening edit
restarts the exact worker sequence until a coherent generation is current.
The interactive parent labels each ordered worker while the worker receives
`--no-progress`; this keeps one stable display without changing phase work or
captured command output.

## security

`security` is the rulepack-driven command family. It takes a workspace and a subcommand.
The compiled-in rulepack is the portable default; `--rules-dir` or
`BONSAI_RULES_DIR` selects a custom/editable base pack.

```bash
bonsai-ninja security ./src taint-analysis --severity high
bonsai-ninja security ./src pack --audit --rules-dir ./security-patterns
```

| Flag or subcommand | Default | Description |
|---|---:|---|
| `<WORKSPACE>` | Required | Workspace root to analyze. |
| `sources` | None | Enumerate source-rule matches. |
| `sinks` | None | Enumerate sink-rule matches. |
| `sanitizers` | None | Enumerate matched rules that can make a credit-bearing sanitizer claim. Passthrough transforms and generic non-crediting validation markers are excluded. |
| `deps` | None | One table row per flagged package the workspace depends on: language, highest rule severity, source/sink/sanitizer role counts, evidence signals (imports, manifests, lockfiles), evidence files, tags. |
| `dependency-analysis` | None | Where each flagged package is used: import sites, the local names they bind, every call or reference through those names, every rulepack match on the package, and every taint-analysis flow the package appears in, rendered like `taint-analysis` with full call stacks. |
| `taint-analysis` | None | Run source-to-sink taint analysis. |
| `source-analysis` | None | Map downstream paths from sources without requiring sinks. |
| `sink-analysis` | None | Map source-independent compiler value lineage into every selected taint-relevant sink. |
| `pack` | None | Audit (`--audit`), list, tree (`--tree`), or validate (`--validate`) the rulepack. |

`pack --validate` checks rule schema, metadata, and `match_examples`. Add
`--taint-replay` to also replay each taint-dependent rule's positive
example through live taint analysis and report any whose own example no
longer fires (`match-example-taint-miss`) — slower, for the deep CI gate.
`pack --audit` reports per-language source-boundary and sink-family coverage;
zeroes are explicit gaps rather than hidden or inferred totals.
Plain `pack` parses every rule YAML and lists the rules grouped the way the
pack is organized on disk — one table per language and kind (sources, sinks,
sanitizers, typing) — with the rule id kept intact, family, tag, severity,
enabled/disabled state, package/framework providers, and description; JSON
returns the same rule rows under `rows`. Narrow the inventory with `--lang`,
`--kind`, `--category`, `--severity`, `--tag`, `--rule <REGEX>` (matches an
id or alias), and `--state enabled|disabled`; the global `--contains` searches
any rule field. `pack --tree` prints the same rules under their YAML file
paths with severity, state, and tag per rule.
See [Rule Testing](./rule-testing.mdx).

`deps` builds the complete dependency inventory for the file scope once and
persists it as a cached object; `--framework`, `--severity`, `--page`, and
`--format` are views rendered from those rows and the loaded rulepack without
opening the workspace again.

`dependency-analysis` is the dependency-centered security view behind `deps`. For every package the
inventory reports, it lists the import statements that bring it in, the local
names those imports bind (`serialize` in `const serialize = require("node-serialize")`,
`S` in `use X\Service as S`, the module tail for plain imports), every call or
reference that reaches the package through one of those names (`serialize.unserialize(...)`),
every rulepack source / sink / sanitizer match whose rule claims the package,
and every complete `taint-analysis` finding the package appears in: a finding whose
source or sink rule claims the package, or whose propagation steps land on one
of its usage sites. The findings come from the same cached complete
taint-analysis report the `taint-analysis` command uses (computed once if it
is not cached yet) and render exactly like that command: `FINDING n` with
source, sanitizer, and sink sides, then the `TAINT FLOW` block with every
hop's source body. Text prints one `PACKAGE n` block per dependency with a
`USAGE SITES` table (`kind`, `location`, `in`, `via`, `code`) followed by its
taint flows; JSON carries the same `rows` with `dependency`, `bound_names`,
`sites`, and `findings` (taint-analysis row shape, flow bodies included). It runs under the same review profile as
`taint-analysis` (test exclusion, excluded paths, severity floor, context), so
both commands share one complete cached taint report, and it projects the
cached complete source, sink, and sanitizer inventories — the same objects
`sources`, `sinks`, and `sanitizers` render — instead of scanning the rulepack
again. `--framework`, `--severity`, `--page`, and `--format` are views over
that result. This is not a package-name heuristic: the taint projection is
joined to exact compiler source/sink/propagation locations and retains the
same finding ids, call stacks, and hydrated bodies as `taint-analysis`.

```bash
bonsai-ninja security ./src dependency-analysis --framework node-serialize
bonsai-ninja security ./src dependency-analysis --severity critical --format json --all
```

Inventory filters are command-specific. The table states exactly where each
flag is accepted; the paging and output controls apply to all inventory
commands.

| Flag | Commands | Default | Description |
|---|---|---:|---|
| `--rules-dir <DIR>` | all | Bundled | Override the base rulepack directory. Also reads `BONSAI_RULES_DIR`. |
| `--rule <RULE>` | `sources`, `sinks`, `sanitizers` | None | Exact rule ID filter. |
| `--rule-regex <REGEX>` | `sources`, `sinks`, `sanitizers` | None | Regex rule ID filter. |
| `--trust <TRUST>` | `sources` | None | Source trust filter such as `remote`, `local`, `service`, `ipc`, `database`, `library`, `config`, or `physical`. |
| `--category <CATEGORY>` | `sources`, `sinks`, `sanitizers` | None | Rule category or canonical family filter. |
| `--tag <TAG>` | `sources`, `sinks`, `sanitizers` | None | Source, sink, or sanitizer tag filter. |
| `--severity <LEVEL>` | `sinks`, `sanitizers`, `deps`, `dependency-analysis` | None | Severity floor: `info`, `low`, `medium`, `high`, or `critical`. |
| `--framework <KEY>` | `deps`, `dependency-analysis` | None | Exact package or framework key. |
| `--file <TEXT>` | all | None | Include only workspace-relative paths containing this text. Repeatable; explicit absolute paths are accepted. |
| `--exclude-file <TEXT>` | all | None | Exclude workspace-relative paths containing this text. Repeatable; explicit absolute paths are accepted. |
| `--limit <N>` | `sources`, `sinks`, `sanitizers`, `deps` | 0 | Maximum rows per page. `0` uses only token-budget pagination; later rows remain reachable with `--page`. `dependency-analysis` pages by package block and has no row cap. |
| `--context <BUDGET>` | all | 32k | Token budget for text and JSON output. |
| `--page <PAGE>` | all | 1 | Page number, `P:xxxxxxxx` cursor, or `next`. |
| `--all` | all | false | Emit all rows without paging. |
| `--format <FORMAT>` | all | text | `text` or `json`. |
| `--output-path <PATH>` | all | stdout | Write the selected `--format` output to a file. |

### `security pack`

`security <workspace> pack` inspects and validates rule data. Listing, audit,
tree, and schema-validation modes do not scan the selected workspace source;
`--taint-replay` additionally compiles each taint-dependent positive example
as an isolated fixture. The workspace operand is still required so rule
discovery has the same deterministic context as the other security commands.

```bash
bonsai-ninja security ./src pack --lang python --category sqli
bonsai-ninja security ./src pack --validate --format json
bonsai-ninja security ./src pack --validate --taint-replay --format json
```

| Flag | Default | Description |
|---|---:|---|
| `--rules-dir <DIR>` | Bundled | Override the base rulepack directory. |
| `--lang <LANG>` | None | Restrict the listing or audit to one language key. |
| `--category <CATEGORY>` | None | Restrict to one tag or rule-ID family. |
| `--kind <KIND>` | None | Restrict to `source`, `sink`, or `sanitizer`. |
| `--severity <LEVEL>` | None | Keep rules at or above one strict severity value. |
| `--tag <TAG>` | None | Restrict to one rule tag such as `command-injection` or `http-input`. |
| `--rule <REGEX>` | None | Rule ID regex; matches the canonical id or any declared alias. |
| `--state <STATE>` | None | Keep only `enabled` or `disabled` rules. |
| `--audit` | false | Render the per-language and per-family coverage audit. |
| `--tree` | false | Group rules by language, kind, family, and source YAML file. |
| `--validate` | false | Validate schemas, metadata, examples, and enabled-rule collisions. |
| `--taint-replay` | false | With `--validate`, replay taint-dependent positive examples through the engine. |
| `--limit`, `--context`, `--page`, `--all` | standard paging | Control presentation only. |
| `--format <FORMAT>` | text | `text` or `json`. |
| `--output-path <PATH>` | stdout | Write the selected output to a file. |

## `security taint-analysis`

The taint command surface is `security <workspace> taint-analysis`.

```bash
bonsai-ninja security ./src taint-analysis --trust remote --tag command-injection
bonsai-ninja security ./src taint-analysis
bonsai-ninja security ./src taint-analysis --minified-js
bonsai-ninja security ./src taint-analysis --profile all
bonsai-ninja security ./src taint-analysis --summary --format json
bonsai-ninja security ./src taint-analysis --flow F:0123456789abcdef
bonsai-ninja security ./src taint-analysis --group G:0123456789abcdef
bonsai-ninja security ./src taint-analysis --format sarif --all --output-path findings.sarif.json
```

Text output is labelled `TAINT FLOW`. Each step is derived from the
finding's source-specific taint path and annotates the source, tainted
argument propagation, receiver evidence where relevant, and sink operand.
When one finding needs more than one page-sized flow unit, every unit retains
the same `FINDING N` number and is labelled `FLOW 1/M`, `FLOW 2/M`, and so on;
the renderer does not introduce a second “continued” numbering scheme.
The bundled `production` profile is the default and applies `trust: remote`,
every sink severity, and common non-production path exclusions. Severity is
not filtered unless `--severity <LEVEL>` is supplied explicitly. `--profile
all` selects the bundled empty profile; local-trust flows remain exact and
their emitted severity is capped at `medium`. Minified input is controlled by
the independent global compiler profile described above. Use `--profile all
--minified-js` together for an unfiltered security audit over every supported
source representation. The inventories (`sources`, `sinks`, `sanitizers`)
and `deps` list the whole workspace regardless of the profile: review
defaults narrow analyses, never the inventory of what exists.
JSON and SARIF findings include `analysis_complete` and
`analysis_incomplete_reasons`; emitted findings are complete semantic
evidence, so complete findings carry an empty reason list. The command has one
canonical semantic analysis contract and one compiler graph: text and JSON
both show how each edge was proven (`resolver_stage`, `evidence`,
`confidence`). There is no precision lattice and no accuracy mode: an edge
either follows from syntax and resolved call flow or it is not in the graph.
Unresolved facts surface as `analysis_incomplete_reasons`, never as findings.

`taint-analysis` computes one complete report — every source rule seeded,
every sink rule as a landing target — and caches it under the semantic
inputs only: workspace content, file include/exclude scope,
`--inferred-sources`, `--exclude-tests`, the rulepack, and the compiler
profile. Every selector is a view over that report: `--source`, `--trust`,
`--category`, `--sink` (and the profile's trust default), `--severity`,
`--tag`, `--finding`, `--flow`, `--group`, `--summary`, `--contains`,
`--page`, `--format`, and `--html-output` re-render the cached report and
never rerun parsing, callgraph, IDG, or taint work. Run the base command
once; every narrowed re-query is a filter over the finished object. Rule selectors match a rule's canonical id or
any declared alias, exactly like the SDK options. Text output
rebuilds flow bodies through one report-scoped source-body cache, plans every
lossless flow unit, and formats only the requested page; JSON hydrates flow
bodies for the rendered rows the same way. Warm source-to-sink scope planning
replays validated partitioned callgraph relations through the same exact
fixed point instead of resolving identical source bodies again; a missing or
rejected relation falls back to compiler body resolution. If source content,
analysis scope, the rulepack, or the cache schema changes, the command
discards the stale report and recomputes it. The progress stream reports the
selected scope and taint-graph cache state so warm runs are explainable
instead of silently appearing to redo work.

| Flag | Default | Description |
|---|---:|---|
| `--rules-dir <DIR>` | Bundled | Override the base rulepack directory. |
| `--profile <PROFILE>` | Rulepack default (`production` when bundled) | Rulepack-declared preset bundle. Use `all` to disable bundled review defaults; combine with global `--minified-js` to admit every supported source representation. Custom packs without `default_profile` remain unprofiled by default. |
| `--source <REGEX>` | None | Source rule ID regex (matches the canonical id or an alias); a view over the complete report. |
| `--finding <S:ID>` | None | Re-render only one stable finding ID. |
| `--flow <F:ID>` | None | Re-render only one security representative taint-path flow ID. |
| `--group <G:ID>` | None | Re-render only findings in one stable security flow group. |
| `--trust <TRUST>` | None | Source trust filter. |
| `--category <CATEGORY>` | None | Source category filter. Use `inferred` for inferred sources. |
| `--sink <REGEX>` | None | Sink rule ID regex. |
| `--severity <LEVEL>` | None | Severity floor. |
| `--tag <TAG>` | None | Sink tag filter. |
| `--file <TEXT>` | None | Analyze only workspace-relative files whose path matches this text. Repeatable. Explicit absolute paths are also accepted. |
| `--exclude-file <TEXT>` | None | Exclude workspace-relative files whose path matches this text. Repeatable. Explicit absolute paths are also accepted. |
| `--inferred-sources` | false | Add synthetic entry-point parameter sources. |
| `--exclude-tests` | false | Drop findings whose source, sink, or proof path is in a workspace-relative test path. |
| `--show-sanitized` | false | Include sanitizer-cleared source-to-sink paths for audit and rulepack debugging. |
| `--include-pattern-only` | false | Include exact source-independent local findings in text/JSON. SARIF enables these automatically. |
| `--context <BUDGET>` | Profile default (`16k` in production) | Token budget. A taint flow remains one continuous numbered block when it fits; only a genuinely oversized flow is divided into explicit page parts. |
| `--page <PAGE>` | 1 | Page number, cursor, or `next`. |
| `--all` | false | Emit every finding. |
| `--summary` | false | Emit only aggregate finding counts. Text shows compact tables; JSON emits the summary object without paged rows. |
| `--format <FORMAT>` | text | `text`, `json`, or `sarif`. SARIF is supported for `taint-analysis` findings. |
| `--baseline <PREV_JSON>` | None | Compare against a previous `taint-analysis --format json --all` file and classify findings as `new`, `unchanged`, or `fixed`. Text appends the three counts; JSON adds `baseline_status` to each current row and a top-level `baseline` object with counts plus any fixed finding IDs. |
| `--explain` | false | Explain why a `--source` / `--sink` pair does or does not connect instead of rendering findings. |
| `--output-path <PATH>` | stdout | Write the selected `--format` output to a file. |

## inspect-graph

`inspect-graph` queries indexed syntax facts and source excerpts that contain the
query or filters, and attaches one bounded compiler evidence unit to every
matching callable: a stable `F:` flow carrying the source body, the resolved
direct callers and callees, and the match point. Every occurrence hit
(call, var, arg, string, import, ref) is indexed against the flow of its
enclosing callable, so the `flow` column always names a compiler flow.
The complete report — declaration hits, occurrence hits, the corridor, and
every taint flow — is persisted as a cached object keyed by the semantic query
(pattern, regex, kinds, `--from`/`--to` and their kinds, `--file`, `--in-fn`).
Every later page, format, view, flow or group selector, and text filter over
the same query renders from that object without re-running the scan or the
taint closures; `show F:`/`G:`/`T:` reopen ids through the same object.
Every rulepack-free taint flow that passes through a matched callable is
listed in the `TAINT FLOWS` table and expanded into its call stack: flows
that share one function chain share one `TAINT CALL STACK` block, which names
every `T:` id it covers and then renders each hop's source body once with the
propagated values annotated, so the reader sees the whole context around a
match without the same body repeated per flow. The stack starts above the
flow's entry with its structural caller lineage — every entry point (a
callable with no caller) that reaches the entry and the callees in between,
one stack per entry-point chain, deepest chain first — taken from one
breadth-first reverse walk over the persisted callgraph (`taint_flows[].lineage` in JSON). Taint closures themselves run
only from the matched callables; the lineage is presentation context, never a
forward closure from every entry point of the repository. It does not load source, sink,
or sanitizer YAML; use `security taint-analysis` for rulepack findings.
Emitted graph facts use the compiler-proven static evidence contract. Raw
taint rows come through the workspace syntax-flow
facade. A warm batch uses its existing IDG target cut; a cold batch builds one
exact query-scoped source/target IDG and falls back to the canonical cached
dataflow graph only when scoped persistence is unavailable. JSON summaries and text
headers report the semantic-flow backend, cache hit/miss counts, target-cut
scope when used, and fallback reasons so warm/cold `inspect-graph` behavior is
visible instead of implicit. For a literal (non-regex) query with taint
flows, `inspect-graph` first validates the persisted retrieval index and takes its
candidate files (trigram pages over the same compiler facts, so never fewer
files than can match) for canonical hydration without reading any source;
if retrieval is absent or stale, it falls back to the exact literal text scan
instead of publishing partial retrieval state.
Broad raw-flow reports compute every requested fixed point before paging, and
format the requested page, its successor, and every page of a report up to 12
pages so page turns replay from the cache. Conservative row costs are recorded
while closure workers build the rows, so rendering does not serialize or
rescan every path merely to plan page boundaries. Follow the printed page or
cursor to continue; `--all` changes presentation only.

Keep lookup and relational questions separate. A plain `inspect-graph --query`,
`refs`, or `calls` query is the lightweight choice for locating a symbol or
call site; `inspect-graph`'s bounded callable evidence never recursively enumerates
caller/callee path combinations. Each declaration hit already carries the
standalone callable packet (see "Declaration facts" below). When both ends
are known, use `inspect-graph --from ... --to ...` for the exact compressed
compiler corridor.

```bash
bonsai-ninja inspect-graph ./src --query os.system --kind call
bonsai-ninja inspect-graph ./src --from handle_request --to os.system --view grouped
bonsai-ninja inspect-graph ./src --from Source.run --to Target.run
```

Corridor. A `--from`/`--to` pair resolves every matching compiler callable
identity and projects the exact compressed compiler corridor between them:
the forward-reachable ∩ backward-reachable cut of the resolved callgraph, with
no path enumeration. Text opens with a `CORRIDOR` section: the corridor's
callables in call order, its resolved edges (`E:` id, caller → callee, call
site, call text, dispatch and resolver stage), and, when `--to` names an
external API rather than a workspace callable (`--to os.system`), the
terminal call sites the corridor ends at inside their enclosing callables.
A `CORRIDOR FLOW 1 F:<id>` block then renders every corridor callable's source
body in call order, with `[FLOW 1 -> callee]` markers on each resolved hop and
a `TO:` marker on the terminal call. Raw taint flows are seeded from the
source callable, so multi-hop taint paths that reach the target appear in
`TAINT FLOWS` too. JSON carries the same facts as `corridor`
(`from`, `to`, `node_count`, `edge_count`, `nodes`, `edges`,
`terminal_calls`, `backends`, `idg_available`, `idg_semantic_edges` for the
warmed-IDG semantic cross-call edges consulted, `analysis_complete`,
`analysis_incomplete_reasons`, and `stack`, an expanded flow whose
`functions` are the callables paged on the current page). Each corridor callable is one pageable unit, ahead of the taint
and hit units. Use `Owner.member` to disambiguate same-named methods;
connectivity, not a single-result name lookup, selects the surviving pair.

Declaration facts. Every `decl` hit carries the bounded compiler packet for
its callable, without recursive expansion: `signature`; `direct callers` and
`direct callees` as compiler-resolved edges, one per line with a stable `E:`
edge id, the other endpoint, the call site, the call text, and the dispatch
plus resolver stage
(`E:<8-hex> <name>  <file>:<line>:<col>  <call text>  <dispatch> · <resolver_stage>`);
`external calls`, the call sites that have candidates but no compiler-proven
target, each with its reason; and `imports`, the file imports the body can
reach. Edge lines are linear in direct graph degree; diamonds and cycles
cannot multiply into a path set. JSON exposes the same facts on
`decl_hits[].value` as `signature`, `direct_callers`, `direct_callees`,
`external_calls` (omitted when empty), and `imports` (omitted when empty).
Reopen an edge id with `show E:...` for full resolver provenance.

## show

`show` resolves a stable bonsai ID and re-opens the owning drilldown view.
It delegates to `inspect-graph`, `dump-taint`, `dump-edges`, `dump-ast`,
`dump-resolve`, or `security taint-analysis` depending on the ID prefix
and supplied context. Raw inspect `T:` ids use `inspect-graph`; structured
dump-taint propagation `T:` ids require `--taint-source` and use
`dump-taint --taint`. `F:` and `G:` ids are shared by structural inspect
flows/groups and security taint-path flows/groups: `show F:...` and
`show G:...` try the structural `inspect-graph` owner first, then fall back to
`security taint-analysis --flow F:...` / `--group G:...` when the id
belongs to a security finding.
Stable IDs are validated before any workspace or rulepack work: `F:`, `G:`,
and `S:` use exactly 16 lowercase hexadecimal characters; `T:`, `E:`, `N:`,
and `R:` use exactly 8. Malformed IDs fail immediately with the required
shape.

```bash
bonsai-ninja show ./src --id F:0123456789abcdef
bonsai-ninja show ./src --id S:0123456789abcdef --rules-dir security-patterns
bonsai-ninja show ./src --id R:aabbccdd --query execute
bonsai-ninja show ./src --id T:aabbccdd --taint-source update_user --taint-seed token --taint-seed action
```

| `F:` | `inspect-graph --flow` structural drilldown or security `taint-analysis --flow` drilldown | Rulepack via `--rules-dir` only when the id belongs to a security finding |
| `G:` | `inspect-graph --group` structural drilldown or security `taint-analysis --group` drilldown | Rulepack via `--rules-dir` only when the id belongs to a security finding |
| `T:` | raw inspect taint path (`inspect-graph`), or structured `dump-taint` propagation | `--taint-source` plus original dump-taint filters for structured propagation ids |
| `E:` | `dump-edges --edge` call-edge provenance | None |
| `N:` | `dump-ast --node` AST-node drilldown | Optional AST scope inherited by the delegated command |
| `R:` | `dump-resolve --candidate` resolver candidate | `--query <QUERY>`, and `--in-file` when the original resolve was file-scoped |

## export

`export` writes the analyzed workspace graph to stdout, or to
`--output-path` when provided.

```bash
bonsai-ninja export ./src --output-path index.json
bonsai-ninja export ./src --format graphml --output-path graph.graphml
```

| Flag | Default | Description |
|---|---:|---|
| `<WORKSPACE>` | Required | Workspace root. |
| `--full-propagations` | false | Force exhaustive interprocedural propagation records. |
| `--format <FORMAT>` | json | `json`, `networkx`, `graphml`, or `cypher`. |
| `--output-path <PATH>` | stdout | Write the selected export format to a file. |

Native export never enumerates a capped prefix of call paths. The resolved
callgraph is the exact linear-space representation of that path language, so
the default includes the complete `compiled_idg` relation without an
exponential materialization step.
The artifact is exact for the selected compiler-input profile. Default export
omits adapter-classified minified JavaScript/TypeScript; add global
`--minified-js` to include bundle internals. This selection changes source
scope, never graph depth, fixed-point work, or path completeness within that
scope.
Native JSON schema v12 carries the code with its graph: `files[].source` is
the full file text and every `span`, `line`, `start`, and `end` in the
document indexes into it; `decls[]` carry their byte span; `callgraph[]` edges
carry the exact `call_text`; `taint_graph.functions[]` carry `end_line`; and
every propagation record carries `call_column` and `call_text`. A consumer
can therefore replay any call stack — entry, every hop's call site, the sink
— with its exact source lines from the document alone, which is what a
training pipeline or a graph database needs. Every code location is
workspace-relative; the top-level `workspace_root` is the sole absolute
anchor, so artifacts stay portable between hosts and no machine-specific
prefix leaks into graph identities or agent prompts. Its machine-readable
Draft 2020-12 contract is
[`schemas/bonsai-native-export-v12.schema.json`](../schemas/bonsai-native-export-v12.schema.json).
A one-shot cache miss streams directly to the selected output; use
`cache rebuild <workspace> --export` only when repeated exports justify a
persisted copy.
Whole-repository native JSON can be a multi-gigabyte, minutes-long artifact;
write it with `--output-path` rather than placing it in an agent context. The
current production-scale time, size, and memory measurements are recorded in
[Release Readiness](RELEASE_READINESS.md#production-scale-native-export-measurement).

## `security source-analysis`

The source-analysis surface is `security <workspace> source-analysis`.

```bash
bonsai-ninja security ./src source-analysis --trust remote
bonsai-ninja security ./src source-analysis --format json --all
```

Text output is labelled `SOURCE n · DOWNSTREAM FLOW m` and keeps the source
rule id on each flow header. The command runs taint forward from each matched
source seed, so it maps where that source value travels without requiring a
sink rule. Internally it uses resolved callgraph lineage scopes and scoped IDG
graphs; it does not walk the entire workspace separately for every source.

Like `taint-analysis`, source-analysis reports scan scope and taint-graph
cache hit/miss notes on stderr while progress is enabled. JSON stdout and
`--output-path` payloads remain clean.

The source reachability closure is exact and every lineage the closure
recorded is emitted as its own flow; there is no hop or path cap, and `--all`
changes only presentation. Every source rule is analyzed once and the complete
report is cached under the analysis scope (workspace content, file
include/exclude scope, `--exclude-tests`, `--inferred-sources`, rulepack);
`--source`, `--trust`, `--category`, and `--tag` are views over that cached
report, so a narrowed re-query never reruns the fixed point.

## `security sink-analysis`

The sink-analysis surface is `security <workspace> sink-analysis`.

```bash
bonsai-ninja security ./src sink-analysis --severity high
bonsai-ninja security ./src sink-analysis --sink '^python\.cmdi\.' --format json --all
```

The command matches each selected taint-relevant sink once, then maps the
exact source-independent value lineage feeding it through the same
Tree-sitter, resolver, and sparse-IDG fixed point used by taint-analysis. It is
the inverse investigation view of source-analysis, not a vulnerability
verdict. Selected security-source proofs are reported separately under
`security_source_flows`; source filters never remove `upstream_flows`.
The text header and JSON `summary.severity_floor` report an effective
sink-severity floor when one is configured explicitly or by a custom profile.
The bundled default has no severity floor, so `security sinks`,
`sink-analysis`, and `taint-analysis` retain lower-severity endpoints unless
the caller supplies `--severity`.

The command computes one report for its sink set — every selected sink
rule, its source-independent lineage, and the security-source proofs for
every loaded source rule — and caches it under the analysis scope (workspace
content, file include/exclude scope, `--exclude-tests`, `--inferred-sources`,
rulepack, and the `--sink` selector). `--sink` is the one scope selector
because lineage is compiled per sink; the complete every-sink object stays
proportional to the sink-relevant call graph, not to entry points × sinks,
because lineage origins are that graph's entry points (admitted functions no
admitted function calls, plus call cycles nothing enters) and one exact route
is kept per direct upstream edge into each sink's function. A sink no entry
point feeds shows the route inside its own function. `--severity`, `--tag`, `--source`,
`--trust`, and `--category` are views over the cached report: severity and
tag keep or drop endpoints, source selectors keep or drop attached proofs,
and a narrowed re-query never reruns the fixed point. The compiler builds one sink-relevant semantic scope,
then validates candidate origins forward against selected sink nodes; it does
not guess a reverse call chain or run a name-based search. Text labels each route
`SINK n · UPSTREAM FLOW m <flow-id> <sink-rule-id>` and presents lineage as
`sink ← … ← origin`; JSON keeps canonical compiler routes under
`upstream_flows` and source-to-sink security proofs under
`security_source_flows`. Pagination selects rendered sink rows only, preserves
global endpoint numbers, and never caps fixed-point work.

manual clearing.

```bash
bonsai-ninja cache stats ./src

```

`index` (after compiling a fresh compiler-object generation, or when the
recorded manifest predates the current schema, root, or source profile),
`index --semantic`, SDK semantic/full-prewarm facades, `cache rebuild`, and
security source/taint analysis runs publish the external-cache `manifest.json`
(currently schema version 8) after they produce reusable sidecars. Besides cache coverage, the manifest records
each source's filesystem stamp and exact text identity, which is what lets a
warm open intern unchanged files without reading them (they load on first
use and are verified against the recorded identity). The manifest is JSON metadata for cache
coverage and fingerprints; command hot paths still use the binary factstores
and validate sidecar headers and payload readability before reuse. Retrieval
sidecars are also checked against the same query-time
source/dependency/schema pipeline fingerprint, so copied or moved candidate
indexes are stale until rebuilt. Retrieval follows the candidate-only
evidence contract defined in
[Architecture](contributing/architecture.mdx#query-browse-trace).
Retrieval sidecars are complete-workspace artifacts; scoped
query opens do not persist partial retrieval snapshots. Path-scoped security
runs likewise keep taint graph reuse in memory for that command and do not
overwrite full-workspace `taint_graph.v*.<mode>.<config>.factstore` files in that cache.
`cache stats --format json` includes the same validation report the
SDK exposes: `manifest_status`, semantic/dataflow/taint/export readiness,
per-sidecar freshness, and stale reasons.
Selective `cache clear --dataflow-only` republishes the manifest immediately,
so the removed optional projection is reported as `missing` while unrelated
semantic sidecars remain fresh; it is never misreported as a stale workspace.

## Browse Commands

Browse commands expose indexed facts. They all open the workspace through the
same hot-refresh path as the SDK, so saved files are refreshed before results
are rendered. Each command's complete row set — every row its semantic filters
select, before any paging — is persisted in the workspace's external cache
(`rows.<key>.json` with a sibling `rows.<key>.bin` blob, keyed by the command and those filters) once it has been
collected. A later `--page N`, `--format json`, `--contains`, or
`--not-contains` over the same filters starts from that row set instead of
collecting again; only the rendered page is projected through the workspace.
Row sets are validated against the workspace content fingerprint and the
binary, bounded in size, and the 24 most recently used sets per workspace are
kept. When a view starts from a cached row set, the command opens only the
files of the rows in its render window instead of ingesting the whole tree
(`calls`, `imports`, `args`, `strings`, `vars`, and `operations` do so unless
`--summaries` is on, whose page costs depend on workspace facts). Plain-text query filters rank exact matches first, then prefix
matches, then broader substring matches before paging spends the render budget;
regex filters keep deterministic structural ordering.
On large workspaces, literal-filtered browse commands first validate a warmed
retrieval sidecar when one exists and use it only to choose candidate files.
The command then runs its normal canonical browse collector on that scope.
Retrieval can narrow `defs`, `calls`, `imports`, `vars`, `strings`,
`comments`, `args`, `operations`, `classes`, `refs`, and `search`; it is not
used to prefilter `entrypoints` because entrypoint status depends on the
whole-workspace resolved call graph.

```bash
bonsai-ninja defs ./src --kind function
bonsai-ninja calls ./src --callee os.system
bonsai-ninja operations ./src --kind write --name token
bonsai-ninja refs ./src --symbol verify_token
bonsai-ninja search ./src --query "request.args"
```

| `--summaries` | false | Add stable callable-summary IDs to browse commands that support them. Text output uses compact labels plus a legend; JSON rows gain a `summary_ids` array. This derives IDs from compiler headers without recursively expanding graph paths. |
| `--format <FORMAT>` | text | `text` or native `json`. |
| `--output-path <PATH>` | stdout | Write the selected `--format` output to a file. |

Summary columns are opt-in semantic navigation labels: exact compiler
identities only, never unresolved fan-out. `defs`, `calls`, `imports`, `vars`,
`strings`, `args`, `operations`, `classes`, `refs`, and `search` support
`--summaries`; lightweight syntax rows remain the default. Native JSON preserves each
command's ordinary row shape unless the flag is present, then adds a `summary_ids`
array to every emitted row. Dense text tables render compact local labels
(`F1`, `F2`, ...) and print a `symbol summary ids:` legend below the table with
the complete copyable `F:<16-hex>` ids. Open one with `show F:...`, or run
`inspect-graph --query` on the callable; use `inspect-graph --from ...
--to ...` when the question is transitive reachability.

Every browse command also renders a `used in (cross-module)` text section for
callable rows on the current page. It lists only incoming callgraph edges
resolved by the compiler, joined to the exact target declaration (not merely
the target file), including the stable `E:` edge id and call-site location; an
empty section explicitly reports that no cross-module callers were proven.
Native JSON carries the same page-scoped projection as top-level `used_in[]`
entries shaped as `{file, callers_in[]}`. Paging changes only which page's
files are projected; it never turns this into name matching or path
enumeration.

## Navigation

`tree` is the workspace module map: a filesystem tree where every file row
carries its language, its named callable and type counts, and its external
import count, followed by one aligned link line per direction — `→` the
workspace files it imports or calls into, `←` the workspace files that call
into it. Directories aggregate the files and callables below them. Module
bodies and lambdas count as compiler callables in JSON but are left out of
the text counts.
Edges come from the persisted partitioned callgraph (one pass) or the resident
resolved graph on a small workspace; there is no path enumeration. Only the
files the tree actually renders are projected, so `--max-depth` and the child
limit bound the compiler work as well as the listing. On a large
workspace with no persisted callgraph yet, `tree` stays a plain listing and
reports `tree-connections-unavailable`; run `index --semantic` once to publish
the partitions. `--files-only` skips the compiler facts on purpose.

`read-file` opens only the selected file and renders the same connections
inline: an `imports` block (bound names, resolved workspace files, use counts
and the lines where each binding is used), a `connections` block of resolved
cross-file edges grouped by the other file with stable `E:` ids, `CALL→` /
`→CALL` line marks on every call site or declaration the edges touch, and a
`USES` mark under every line that goes through an imported name (which import,
and the workspace file it resolves to). Findings, taint flows, and inlined
cross-file bodies remain explicit overlays.

```bash
bonsai-ninja tree ./src --max-depth 3
bonsai-ninja tree ./src --files-only
bonsai-ninja read-file ./src --file auth/verify_token.py
bonsai-ninja read-file ./src --file auth/verify_token.py --lines 1:80 --from request.args --to os.system
```

| Command | Purpose | Key flags |
|---|---|---|
| `tree` | Workspace module map: files with declarations, resolved imports, and cross-file call edges in both directions. | `--max-depth`, `--file`, `--exclude-file`, `--limit`, `--files-only`, `--context`, `--page`, `--all`, `--format`, `--output-path` |
| `read-file` | File view with inline module connections (imports, cross-file edges, `CALL→`/`→CALL` marks); findings and cross-file bodies are explicit overlays. | `--file`/`--path`, `--symbol`, `--lines`, `--from`, `--to`, `--max-inlined-bodies`, `--compact`, `--context`, `--page`, `--all`, `--format`, `-o`/`--output`/`--output-path`, `--rules-dir` |

JSON includes top-level `analysis_complete` and
`analysis_incomplete_reasons`. `tree` file nodes carry `connections`
(`language`, `decls[] {name, kind, line}`, `imports[] {module, names, line,
wildcard, resolved_files, uses}`, `calls_out[]` and `callers_in[]` as
`{file, edges[] {edge_id, caller, caller_line, callee, callee_line, line,
column}}`); directory nodes carry `files_below` and `decls_below`; the summary
adds `total_decls` and `total_cross_file_edges`. Structural depth and child
limits mark the tree incomplete; use `--all` and avoid restrictive
`--max-depth` when you need every node. `read-file` JSON carries
`connections {imports, calls_out, callers_in}` in the same shapes, and its
`marks[]` include `call_out` / `call_in` entries with `edge_id` and `target`, and
`import_use` entries whose `at.decl` names the binding and `tag` the module;
`imports[].use_lines` lists the lines a binding is used on.
Finding digests repeat their own completion fields. Semantic overlays are
enabled only by `--rules-dir`, `--from`, `--to`, or
`--max-inlined-bodies`. Once enabled, connected caller/callee bodies are
uncapped by default; `--max-inlined-bodies <N>` is the explicit body cap and
`0` is uncapped. `--all` only disables output pagination; it does not enable
semantic work or change the body scope. Explicit minified source access uses
the global compiler-input contract: add `--minified-js` to `read-file`.
A cold `read-file` on a workspace of at most 5,000 files opens the complete
lazy index so cross-file edges resolve; above that it keeps the single-file
open and reports the missing persisted callgraph. After semantic indexing the
default path reuses the selected file's exact content-addressed compiler body
by its stable full-workspace `FileId` and answers connections from the
persisted partitions. All rendered `read-file` locations, including HTML
reports and nested semantic overlay locations, are workspace-relative and
rehydrate through the canonical VFS join rather than basename matching.

## Debug Dumps

Dump commands expose the engine's internal facts. Use them when `inspect-graph` or
security output disagrees with the source.

```bash
bonsai-ninja dump-ast ./src --file gateway.py --function handle_request
bonsai-ninja dump-hir ./src --symbol handle_request
bonsai-ninja dump-taint ./src --source handle_request --seed cmd
```

| Command | Purpose | Key flags |
|---|---|---|
| `dump-ast` | Tree-sitter parse tree by file, function, or stable `N:` node id. | `--file`, `--function` (or positional function), `--compact`, `--max-depth`, `--node`, `--context`, `--page`, `--all`, `--format`, `--output-path` |
| `dump-hir` | Flow-event tree for one function, grouped by compiler structure in text or as one structured object with `--format json`. | `--symbol` (preferred), positional symbol, `--format`, `--output-path` |
| `dump-cfg` | Basic-block CFG for one function, grouped by block in text or as one structured object with `--format json`. | `--symbol` (preferred), positional symbol, `--format`, `--output-path` |
| `dump-callgraph` | Per-function caller and outgoing counts with exact source line/column locations in both JSON and text; JSON also retains the byte anchor. | `--limit`, `--context`, `--page`, `--all`, `--format`, `--output-path` |
| `dump-edges` | Resolved call edges with stable `E:` ids, resolver stage, evidence, and confidence. | `--from`, `--to`, `--compact`, `--edge`, `--limit`, `--context`, `--page`, `--all`, `--format`, `--output-path` |
| `dump-resolution` | Per-file and per-decl call resolution coverage from shared `FlowEvent::Call` facts and canonical callgraph edges; nested declaration rows are paged as one lossless table. | `--file`, `--unresolved-only`, `--limit`, `--context`, `--page`, `--all`, `--format`, `--output-path` |
| `dump-resolve` | Resolver stages and candidates for a name. | `--name` (preferred), positional name, `--in-file`, `--compact`, `--candidate`, `--format`, `--output-path` |
| `dump-taint` | Taint propagation records from one source function with stable `T:` ids. | `--source`, `--seed`, `--sink`, `--compact`, `--taint`, `--context`, `--page`, `--all`, `--format`, `--output-path` |
| `diagnostics` | Adapter diagnostic report with parser diagnostics, workspace languages, and per-language capability/evidence tables for adapters present in the workspace; readable text by default, one structured object with `--format json`. | `<WORKSPACE>`, `--format`, `--output-path` |

`dump-resolution` is a language-agnostic resolver honesty view. It compares
adapter-emitted call sites against the resolved semantic callgraph and reports
resolved workspace calls, known external/library API calls, unresolved calls,
dynamic calls, macro calls, and receiver-type-gap counts without inventing
edges. `coverage_percent` is workspace-resolution coverage:
`resolved_call_sites / (resolved_call_sites + unresolved_call_sites)`, so
import-proven external calls are visible as `external_call_sites` but do not
masquerade as missing workspace edges. Native export applies the same
classification when it streams a persisted callgraph, so warming the cache
cannot change `analysis_complete` or its reason counts.

`dump-taint --format json` includes top-level `analysis_complete` and
`analysis_incomplete_reasons`. The IDG-backed path computes the requested
semantic closure exactly; compatibility budget flags do not cap evidence.
