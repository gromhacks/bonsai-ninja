# Solidity Support

Solidity is supported, but it is not treated as a normal app/web taint
language.

bonsai-ninja still parses Solidity, builds navigation facts, resolves
contract and function structure where the adapter can, and exposes those
facts through the same browse, inspect, trace, export, and security
commands as other languages. The difference is the security rule
taxonomy.

For general-purpose languages, the bundled rulepack uses the canonical
app/web source-sink-sanitizer families: command injection, SQL
injection, XSS, SSRF, path traversal, header injection, and related
classes. Solidity does not have a shell, filesystem, SQL/LDAP/XML
clients, HTML rendering pipeline, or web redirect surface in the same
sense. Forcing those categories into Solidity would create fake coverage
and misleading gaps.

The Solidity pack is a smart-contract pack. Its rules target on-chain
hazards such as:

- reentrancy and external value-forwarding calls
- unrestricted `delegatecall`
- `selfdestruct` / legacy `suicide`
- unchecked low-level call results
- weak authorization and ownership transfer patterns
- oracle and spot-price misuse
- block timestamp / blockhash randomness
- signature replay and hash-collision patterns
- token mint/burn/transfer hazards
- deterministic-address / CREATE2 risks

`security pack --audit` therefore marks Solidity as
`security_model: "smart-contract"` and sets
`canonical_sink_families_applicable: false`. That is intentional. It
means Solidity is audited against its own domain taxonomy, not against
the app/web sink-family matrix.

Use Solidity findings as smart-contract review leads. Do not add stub
SQLi/XSS/SSRF/path/command rules for Solidity unless the rule models a
real EVM or on-chain security boundary.
