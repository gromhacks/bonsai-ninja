# Security analysis specification

The `bonsai_security` crate operationalises the taint engine into a SAST
tool. It loads YAML rulepacks, matches rules against workspace facts,
drives the engine to produce findings, and renders SARIF / JSON / text
reports.

If you're authoring rules, start with [Pattern Guide](pattern-guide.mdx). This doc is
the engine-side spec - what `bonsai_security` does with rules, how
findings flow, how IDs are stable.

## Rulepack layout

```
security-patterns/
└── langs/
    └── <lang>/
        ├── sources/<family>.yml
        ├── sinks/<family>.yml
        ├── sanitizers/<family>.yml
        └── typing/<family>.yml
```

Two layouts work: the canonical `langs/<lang>/{sources,sinks,sanitizers,typing}/`
where the rule kind comes from the directory, and a flat custom layout
where each YAML file declares `language:` explicitly. `RuleKind` is always
derived from the directory - never declared in YAML.

## Rule schema essentials

Required for every rule:

- `id` - globally unique within (language, kind).
- `language` - one of the 20 supported languages.
- `match.kind` - `call`, `new`, `read`, `write`, `return`, `param`, or
  `missing`; typing rules may additionally use `type`.
- `match.callee` (call/new) or `match.target` (read/write/return/param)
  - at least one structural selector such as `name`, `attribute`, `regex`,
    `annotation`, `default_call`, or `call_kind_in`.
- `description` - at least 15 chars, explains the API and risk.
- `match_examples` - at least one entry whose `code` triggers the rule.

Sinks also need `cwe: [CWE-NNN]` and `severity: low|medium|high|critical|info`.
Sources also need `trust: remote|local|service|ipc|database|library|config|physical`.
Use source `tag` values to describe the trust boundary, not the sink
class; for example `network-input`, `archive-input`, `graphql-input`,
`env-input`, or `cli-input`.

Typing rules declare at least one non-finding compiler model:

- `returns_type` plus a structured call/new match declares a factory or
  constructor result type.
- `callback_param_types` plus `match.kind: call` and
  `callback_arg_index` declares an external signature for an inline callback
  argument.
- `callback_param_types` plus `match.kind: type` declares an external
  functional-interface/callable signature; `callback_arg_index` is omitted.
- `taint_semantics` declares a library transfer summary.

Typing rules never emit findings, source/sink inventory rows, or SARIF
results. Adapters provide exact callback bindings and declared source types;
API names and external parameter types remain rulepack data rather than a
hardcoded engine list. Type matching is exact and case-sensitive.

A structured `match.kind: new` target is also the rulepack's exact declaration
that the selected external call is a constructor. This matters for grammars
such as Kotlin where constructors and functions share one CST call shape.
Constructor identity does not implicitly type the result: add `returns_type`
in a non-finding typing rule when a later receiver needs that type. Shared
matching never treats capitalization as constructor or type evidence. The
typing rule's import/package constraints remain mandatory for result typing.
Exact workspace resolution runs before an external constructor model: values,
ordinary functions, mixed candidates, and ambiguity shadow or reject that
model, while an unresolved provider call may use the structured YAML identity.

`call_kind_in` selects a typed operation lowered by the active Tree-sitter
adapter. For example, `[index_write]` represents `receiver[key] = value`
without inventing a runtime method name. Pair syntax-only call kinds with
rule-owned receiver/package/type constraints; shared matching never maps them
to a framework API.

## Disabled rules

Disabled rules need a reason:

```yaml
enabled: false
disabled_reason:
  code: subsumed | over-broad | requires-constraint | pending-adapter-fact
  subsumed_by: other.rule.id   # required when code: subsumed
```

`subsumed_by` chains terminate at an enabled rule. The validator catches
broken chains.

## Capability-gated loading

The matcher reads each adapter's `LanguageCapabilities` (see
the internal coverage baseline at rulepack load time. A rule that anchors on
a construct the adapter declares `Unsupported` is rejected - typically
with `disabled_reason.code: pending-adapter-fact` - so it can't fire on
shapes the engine wouldn't analyse precisely.

Recent capability promotions unblock several rule families:

- **Macros** in C / C++ / Objective-C - Unsupported -> Partial. Rules
  anchored on `STR_CPY`, `LOG`, `assert`, `NSAssert` shapes load.
- **Reflection** in Python - Unsupported -> Partial. Constant-string
  `getattr` / `setattr` / `hasattr` are rewritten to direct attribute
  calls.
- **Reflection** in Java - Unsupported -> Partial. The
  `Class.forName("X").getMethod("Y").invoke(...)` chain rewrites to a
  synthesized `X.Y(...)`.
- **Exceptions** in Java / Kotlin / C# - Partial -> Exact. Rules that
  anchor on a specific catch arm fire only when the throw type can
  plausibly be caught.

## Match shapes

| Shape           | Example             | Notes                                                                   |
| --------------- | ------------------- | ----------------------------------------------------------------------- |
| `name`          | `name: get`         | Bare callee - pair with `packages:`.                                    |
| `attribute`     | `[requests, get]`   | Fully-qualified path. Alias-aware.                                      |
| `regex`         | `^.*\\.body$`       | For variable receivers with a fixed verb.                               |
| `base_name_in`  | `[args, variables]` | Optional base/receiver identifier filter for receiver-agnostic regexes. |
| `annotation`    | `RequestParam`      | Walks `Decl.param_annotations`.                                         |
| `default_call`  | `Body`              | Param-only: matches the direct default call from `Decl.param_default_calls`. |
| `decl_kind_in`  | `[method]`          | Param-rule filter over adapter-emitted `Decl.kind`.                     |
| `visibility_in` | `[public]`          | Param-rule filter over adapter-emitted `Decl.visibility`.               |

Scope qualifiers `in_class` and `in_method` consult `Decl.parent` and
`Decl.bases`, so a class `WebSocketHandler` matches subclasses as well.
`Decl.parent` is adapter-derived AST ownership; rule matching does not
recover class membership from source-span containment.
Param-rule qualifiers `decl_kind_in` and `visibility_in` are also
adapter facts; they should be used when a source applies only to public
entrypoints and not to same-named internal/helper parameters.
`default_call` is the rule-owned bridge for source-language forms such as
Python `payload: dict = fastapi.Body(...)`: the adapter records the direct
callee without knowing FastAPI, while the rule assigns the API its security
meaning. When a parameter target declares both `annotation` and
`default_call`, they are alternative source-syntax selectors; this lets one
rule cover `Annotated[..., Body()]` and `value = Body(...)` without duplicating
the security identity.

## Constraints

Constraints are post-filters applied after the basic match. All must pass.

| Constraint | Effect |
|---|---|
| `receiver_type_in: [HttpClient, Request]` | Receiver type fact must match one of the listed types. Preferred whenever the receiver is typed — from annotations, fields, or a local constructor assignment (`x = Pkg.Class(...)`). A receiver-agnostic callee regex plus this constraint stays precise without relying on the package gate alone. |
| `arg_equals: { index, value }` | Arg N must equal `value`. |
| `arg_tainted: { index \| kw }` | Engine must prove the named arg flows from a source. |
| `receiver_tainted: true` | Engine must prove the call receiver flows from a source. |
| `any_arg_tainted: true` | Engine must prove at least one syntactic arg flows from a source. |
| `receiver_factory_argument_fields_equal` | The call receiver must be an immutable compiler place initialized by the rule-declared factory, with the selected aggregate argument containing every declared exact typed field. The proof follows lexical ownership, rejects sibling-scope bindings, spreads, ambiguous factory/configuration facts, and any later receiver or receiver-field assignment. When the rule declares `imports`, the factory binding itself must resolve through one of those exact compiler import aliases; a same-named local factory fails closed. |
| `keyword_arg_equals: { name, value }` | Named arg equals. |
| `arg_matches_regex: { index, regex }` | Arg N matches regex. |
| `arg_not_matches_regex: { index, regex }` | Arg N must NOT match regex (exclude escaped / constant-built args). |
| `any_arg_matches_regex: <regex>` | Any argument matches regex (varargs / option bags). |
| `format_arg_index: N` | Treat arg N as a format string. |
| `top_level: true \| false` | Match must (`true`) or must not (`false`) be at module top-level. |
| `arg_count: N` / `max_args: N` / `min_args: N` | Exact / upper / lower argcount bounds. |
| `enclosing_decorator_in: [name, ...]` | Enclosing decl carries one of the listed decorators. |

`arg_tainted` is intentionally narrow. For `call` and `new` rules it
evaluates syntactic call arguments against engine `TaintedCallKind::Call`
records - that includes real `FlowEvent::Call` arguments and nested
receiver calls extracted from chains. For `write` rules it may also evaluate
the synthetic write operand, where `index: 0` is the assignment RHS. This
lets assignment sinks require a tainted value without encoding library API
names in the engine. Return records and other diagnostic operands may render
in traces but cannot satisfy an `arg_tainted` sink constraint.

Source-independent API/config misuse rules should not fake taint
constraints. Examples include disabled autoescape, permissive resource URL
configuration, and weak crypto/random API calls. Keep those as local pattern findings; source-to-sink rules for
injection, path, command, queue, header, XSS, and prototype-pollution data
sinks should name the vulnerable tainted operand explicitly.

Classify the actual parser boundary. For example, explicitly enabling
`fast-xml-parser` internal/named entity processing is a medium CWE-776
entity-expansion hazard. It is not CWE-611 evidence that the library resolves
external `SYSTEM` entities, and neither a configured constructor nor a tainted
`.parse(...)` call alone is sufficient. The JavaScript and TypeScript rules
therefore join the tainted parse operand to an immutable receiver initialized
by `XMLParser` with the compiler-decoded exact field
`processEntities: true`. Explicit `false`, mutable/ambiguous configuration,
unused configured parsers, and unconfigured tainted parsers remain negative.
The finding is attributed to the proven configuration span while its code
flow retains the real parse call and tainted argument.

Do not classify `new XSSFWorkbook(InputStream)` as an Apache POI XXE sink.
Apache POI's historical CVE-2019-12415 boundary was the versioned
`XSSFExportToXml` conversion path before 4.1.1, not ordinary workbook
construction. Java, Kotlin, and Scala keep the legacy constructor-shaped rule
disabled with this rationale. Archive bombs and duplicate ZIP entries require
separate version/configuration-aware rules; neither is evidence of CWE-611.

Use `receiver_tainted: true` for receiver-state sinks where the security
operand is left of the call operator, such as Scala `cmd.!`. Use
`any_arg_tainted: true` only when every
argument is an equivalent payload surface.

Rules whose risk names a specific argument **must** constrain that
argument:

- Bounded-copy memory rules - `memcpy(dst, src, n)` needs
  `arg_tainted: { index: 2 }`. A fixed `FIXED_LEN` is not evidence of
  CWE-120 because `dst` or `src` is tainted.
- Allocation-size rules - `malloc(n)` / `alloca(n)` index 0, `realloc(ptr,
  n)` index 1, `aligned_alloc(align, size)` index 1, `calloc(nmemb,
  size)` needs separate rules. Tainted pointer reachability is not a
  tainted allocation size.

## Taint Semantics

Rules can declare taint-transfer details when the vulnerable API shape
is not simply "return value is tainted" or "arg N is tainted."

| Field | Rule kind | Effect |
|---|---|---|
| `taint_semantics.source_output_args: [N, ...]` | source | Treat only the listed call arguments as tainted outputs. Use for out-buffer APIs such as `recv(fd, buf, len, flags)`, `SSL_read(ssl, buf, len)`, and `fgets(buf, size, stdin)`. |
| `taint_semantics.call_result_passthrough_args: [N, ...]` | sanitizer/passthrough | Treat the listed call arguments as flowing unchanged to the call result. Use for decode/unescape APIs that preserve attacker control while changing representation. |
| `taint_semantics.call_result_passthrough_receiver: true` | sanitizer/passthrough | Treat the method receiver as flowing unchanged to the call result. Use for receiver transforms such as `value.removingPercentEncoding`. |
| `taint_semantics.output_arg_flows` | source/sink/sanitizer/passthrough | Treat selected value arguments as flowing into a listed output argument. Use for formatter/copy APIs that write a tainted payload into a caller-owned buffer. |
| `taint_semantics.clean_output_overwrite` | sanitizer | Treat an output argument as clean when the configured value inputs are clean. |
| `taint_semantics.taint_receiver_from_args: true` | sink | Treat tainted arguments as mutating the receiver state for later `receiver_tainted` sinks, using the rule's structured callee target. |

For a receiver-mutating rule with an external `receiver_type_in` constraint,
security first compiles the rule through the canonical AST matcher. A call is
admitted only after its imports, package evidence, call kind, exact external
typing, and workspace-shadowing checks succeed. The resulting exact call span
is part of the IDG transfer fingerprint; the IDG does not match the library
name itself. This rule match proves the receiver identity only—the fixed point
must still prove that the configured argument is tainted before receiver state
changes.

`source_output_args` is intentionally narrow. It prevents source calls
from tainting unrelated operands such as file descriptors, size
arguments, flags, or handles while still introducing taint at the source
call site for the real output buffer.

`call_result_passthrough_args` and `call_result_passthrough_receiver`
keep representation-changing APIs configurable in the rulepack. The
engine supplies the generic mechanism: if a configured argument or method
receiver is tainted at a matching call, the call return is tainted. The
API name and transfer shape stay in YAML so projects can add or remove
decode/unescape or case-normalization models without rebuilding the
engine. Matching normalizes the common qualified-name separators
(`.`, `::`, `->`, and Erlang `:`) before comparing rulepack callees with
adapter-emitted call text.

`output_arg_flows` handles APIs where the dangerous value is written
into an argument rather than returned. Each entry declares
`output_arg_index` plus either `value_start_arg_index` or
`value_arg_indices`. If any configured value argument is tainted at a
matching call, post-call reads of the output argument are tainted. API
names and argument indices stay in YAML; the engine has no built-in
formatter or copy function table.

`clean_output_overwrite` is the overwrite counterpart: the configured
output argument gets a fresh writer at the call site. Clean configured
value inputs leave that writer clean, while tainted configured value
inputs still flow into it. This prevents stale buffer taint from leaking
past a real overwrite without turning formatter APIs into hardcoded
engine sanitizers.

## Receiver Context

Structured attribute rules match exact API paths or semantic receiver
types. `[Eta, render]` matches `Eta.render(...)`; `engine.render(...)`
matches only when adapter facts prove `engine` has receiver type `Eta`.
Regex callees follow the same contract: after direct canonical-name matching,
the matcher may compare `DeclaredReceiverType.method` synthesized from the
adapter's receiver-type facts. It never infers the type from a variable name
or embeds a library inventory in shared Rust.

Receiver/class-shaped rules that declare adapter-visible `packages:`,
`imports:`, or `modules:` are gated at the call site. This includes
receiver-agnostic regexes, typed attributes, and constructor-name rules.
The matcher expands callee text, import aliases, declared receiver types,
and receiver-type import aliases before comparing package signals. A
file-wide import alone is not enough for those shapes to match. Exact
global builtins such as `exec()` stay package-independent even when a
merged compatibility alias lists package metadata.

## Finding lifecycle

```
matched sources         matched sinks
       │                       │
       ▼                       ▼
[gather + filter]      [gather + filter]
       │                       │
       └────────────┬──────────┘
                    ▼
           build_findings_chain_aware
           (source-specific interprocedural taint)
                    │
                    ▼
              call_records
              tainted_calls
                    │
                    ▼
            attribute to sinks
            (span overlap check)
                    │
                    ▼
          sanitizer credit pass
          (tag -> tag table)
                    │
                    ▼
        combine_findings_by_source_flow
        (group by evidence kind, language, vulnerability class,
         and exact sink site; retain every route)
                    │
                    ▼
              finalize:
              finding_id = FNV-1a-64(
                all source ids, all sink ids,
                representative group id, language)
                    │
                    ▼
            TaintAnalysisReport
```

The finding ID is stable for the complete semantic sink finding across
runs. Different source-to-sink routes do not create duplicate findings:
native JSON retains them in `alternate_flows`, and SARIF emits them as
multiple `codeFlows` on one result.

Security taint analysis builds an exact graph per matched source seed.
The seed set is selected from the per-function value-flow graph and
augmented by strict nearby adapter `FlowEvent` facts. The engine then
records tainted call edges and terminal tainted calls. The cached
workspace dataflow graph is still used by navigation and export surfaces,
but source-to-sink findings and their rendered flow IDs come from this
source-specific taint evidence.

Regression coverage for the May 2026 benchmark gaps is part of the
shipped CLI test suite. The covered shapes include Go and JavaScript
cross-file handler-to-service flows, JavaScript and TypeScript GraphQL
resolver `args.<field>` sources, Python GraphQL arguments reaching
untyped `conn.execute(...)` SQL sinks, browser `document.URL` DOM-XSS
sources, and Java JAX-RS / Vert.x / graphql-java request sources. The
GraphQL JS/TS source rules intentionally match exact resolver receiver
names (`args.<field>` and `variables.<field>`) rather than any object with
a common property name, so sibling values such as `user.id` do not become
tainted just because a GraphQL package is imported.

## Sanitizer credit

Crediting sanitizer matches do not erase IDG reachability. After the engine
emits a complete source-to-sink path, the security layer relates matched
sanitizers and compiler-proven guard summaries to the exact lineage. The
`security-patterns/metadata.yml` maps compatible security contexts and
downgrades or suppresses the finding according to the rule's declared
coverage. Same-tag credit is implicit; cross-tag and explicitly non-crediting
vocabulary live only in `sanitizer_credits`, never in Rust.

This keeps sanitizer attribution conservative: false positives over false
negatives. A sanitizer rule that doesn't match a real call doesn't credit
anything.

Passthrough rules are different. They extend taint through a transform and
never receive sanitizer credit. Text output labels them `TAINT TRANSFORM`;
SARIF code-flow steps use `taint-transform`; structured output stores their
ids in `taint_transform_rule_ids`, separate from `sanitizer_rule_ids`.

### Compiler-proven guard semantics

`analysis_semantics` lets a sink describe a security boundary over exact
adapter IR without hardcoding an API or a language in the engine:

| Field | Exact proof consumed |
|---|---|
| `configured_call_argument_guard` | Exact scalar fields from a structurally complete, spread-free aggregate argument equal the rule's required values. Unrelated dynamic field values stay unknown and do not invalidate an independent exact field. |
| `receiver_configuration_guard` / `configured_argument_receiver_guard` | Unconditional calls configure the exact receiver. `identity_argument_indices` selects the configuration facet, so the latest write to that facet wins without confusing another call to the same setter. |
| `character_constraint` | A constrained alphabet or exact substitution map reaches the selected sink value; SQL rules may also require that value to be enclosed by a particular literal delimiter. Provider-backed transforms receive credit only when their factory, operation, and rule-required mappings all match. |
| `compiler_guard` | An adapter-proven, API-neutral capability reaches the exact matched call. `required_evidence` selects syntax roles such as a callback slot or selector chain; `forbidden_evidence` rejects unsafe static choices. |
| `same_origin_path_constraint` | A unique helper rejects URL schemes and authorities, requires `/`, and rejects `//` before returning the path. Provider-backed parsing is credited only when `accepted_providers` authorizes the adapter-recorded import identity. |
| `dynamic_key_denylist_guard` | A unique helper drops the rule-owned static key set and, when required, recursively rebuilds nested values. |
| `url_reconstruction_guard` | A unique helper parses a URL, restricts scheme and host against static facts, and rebuilds the outbound URL from the declared components. `scheme.reconstructed_values` distinguishes parser spellings such as `https:` from reconstructed spellings such as `https`; redirect policy can require typed fields in a sink option aggregate. |
| `url_network_guard` | Exact parser, scheme/host, DNS resolver, optional address-parser, and private-address predicate roles are rule data. `sink-argument-parser-input` proves the sink consumes the same compiler value that the parser validated. |
| `context_flow.sanitized_rewrite_clears_channel` | A sanitized producer rewrites an implicit channel before its consumer. Straight-line order or a typed non-null branch must prove the replacement, and a later unsanitized write cancels it. |
| `sink_terminal_priority` | Presentation-only collapse of a lower-priority downstream transport sink in the same vulnerability class when an exact resolved call/assignment chain proves both sites belong to one flow. |

The adapter owns Tree-sitter syntax recognition; the rulepack owns API roles
and security values; shared analysis only joins those typed facts. A
provider-bound character fact is ignored unless its recorded factory and
operation match `accepted_providers`. A compiler capability is ignored unless
all required evidence is present and all forbidden evidence is absent.
The same fail-closed rule applies to same-origin facts: a fact that depends on
a runtime parser must match `same_origin_path_constraint.accepted_providers`,
while a syntax-only fact is accepted only when that provider list is empty.
Missing, ambiguous, mutable, or partially decoded evidence never grants
credit. Pack-wide dependency/taxonomy/default policy lives in
`security-patterns/metadata.yml`, not in analyzer source.

Exact aggregate fields are independent proofs, not a claim that every sibling
value is static. For example, `{ timeout: dynamicTimeout, followRedirect:
false }` proves the boolean field when the object has no spread, computed key,
or duplicate path. A spread, dynamic key, duplicate field, missing required
field, or wrong typed scalar fails closed.

Configured character transformers use the same separation. A language
adapter may prove that a factory was configured with a complete sequence of
decoded one-character substitutions and that its result flows through a
particular operation. The sink rule alone declares which factory/operation
identities and complete mapping inventory are security-relevant. Shared
analysis performs an exact join and has no built-in escaper, LDAP, SQL, or
provider names. Extra, missing, duplicate, or mismatched mappings fail closed
because an overlapping replacement could change runtime precedence.

`ConditionExpressionFact::Truthy` represents an exact compiler value tested
for runtime truth, including boolean property reads used by network-address
guards. Falsey fallback expressions retain the dynamic projection selected by
the AST instead of collapsing the expression to a clean literal. Shared guard
analysis consumes this typed tree; it never parses a rendered condition.

Package gates follow the same ownership rule. Every adapter emits canonical
`ImportSpec` and call identities. `metadata.yml` declares that language's
prefix/suffix normalization, component separators, and optional package-tail
binding. Shared package matching applies those declarations generically and
does not know runtime schemes, header extensions, namespace syntax, or a
language id.

Call constraints can also require exact positional aggregate values with
`arg_sequence_items_equal`. The adapter decodes array/list initializer
elements into `StaticScalarValue` entries; dynamic elements remain explicit
`None`. This distinguishes direct argv execution from an explicit `sh -c`
wrapper without parsing source tokens in the matcher.

## Output formats

Three:

- **text** (default) - themed terminal output.
- **json** - stable schema documented in `crates/security/src/report.rs`.
- **sarif** - SARIF 2.1.0 for `security taint-analysis` findings,
  GitHub code scanning, and the CVEBench-SAST harness. SARIF includes
  exact source-independent API/config misuse findings by default; those
  rows have no `codeFlows` and use `pattern:<sink-rule-id>` as their
  source id. Lifecycle-audit transition sites are not emitted as
  findings until later same-value use is proved.

Finding JSON and SARIF are content-stable: the same workspace produces
the same bytes (sorted findings, deterministic `finding_id`s, no
timestamps in the default emission). Stable IDs are exercised by
`crates/security/tests/finding_id_stability.rs`; repeated CLI analysis and
export rendering are covered by `crates/cli/tests/taint_engine_e2e.rs` and
`crates/cli/tests/determinism.rs`.

Each taint finding carries `analysis_complete` and
`analysis_incomplete_reasons`. Public findings are emitted only from complete
semantic evidence today, so the field is normally `true` with an empty reason
list; if a future mode reports incomplete evidence, it must populate the same
fields instead of relying on implicit precision.

## Source-analysis mode

`security source-analysis` runs the engine forward from each matched
source without requiring a sink rule. Useful for "where does this data
go" investigations. The report shape is similar to taint-analysis but
without the sink-attribution stage.

Source-analysis uses the same source-seed extraction and rulepack transfer
semantics as taint-analysis. A source such as `request.args.get("cmd")`
follows the value it introduced, not every parameter, local, or unrelated
branch in the entry function. Before rendering, the command builds a
source-lineage scope from resolved callgraph edges, adds summary-output caller
support for source-returning helpers, and seeds a scoped IDG for only the files
and functions in that lineage. Text output is labelled `SOURCE FLOW` to
distinguish these paths from generic `inspect` call flows.

Each JSON row carries `analysis_complete`, `analysis_incomplete_reasons`,
and `lineage`. If representative lineage rendering hits its hop or path
budget, the row is explicitly marked incomplete instead of being presented
as complete evidence.

## Text flow labels

Text output uses distinct labels for different evidence surfaces:

| Label | Surface | Evidence |
|---|---|---|
| `FLOW` | `inspect` and navigation views | Resolved call/fact reachability. |
| `SOURCE FLOW` | `security source-analysis` | Taint propagation from a source rule without sink attribution. |
| `TAINT FLOW` | `security taint-analysis` | Source-to-sink propagation with tainted args, receiver evidence, sanitizer context, and sink attribution. |

JSON and SARIF expose the same underlying propagation as structured
fields. In SARIF, every complete route is emitted through `codeFlows`; in
native JSON, the representative route lives in `taint_path` and the other
routes live in `alternate_flows`.

## Validation

`bonsai-ninja security pack --validate <path>` lints a rulepack locally
without running analysis. Catches:

- missing `match_examples`,
- examples that wouldn't fire on their own canonical shape,
- broken `subsumed_by` chains,
- severity / CWE typos,
- match shapes incompatible with the language's adapter capabilities.

`security pack --audit` adds the coverage matrix.
