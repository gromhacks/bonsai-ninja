# Language Support

Every language is a compiler frontend, not a filename switch over a shared
string parser. Its adapter selects the Tree-sitter grammar and lowers
language-specific declarations, imports, scopes, calls, receivers,
constructors, branches, assignments, aggregate fields, lambdas, and types into
the common IR. Adapter capabilities also declare module roots, export aliases,
implicit/super receivers, constructor method forms, universal types, and field
place completeness. Shared resolver, callgraph, IDG, security, and export
passes consume those facts without branching on the language id.

The production taint engine computes a sparse monotone fixed point over the
resolved IDG for every supported language. Cross-procedural semantics do not
have a BFS depth, iteration, or result cap. Explicit trace/path previews and
output pages can be bounded for presentation; they report truncation and do
not change the semantic taint result.

The table summarizes bundled security coverage and the most important dynamic
syntax that remains inherently approximate. "Lifecycle" means lifecycle or
state-machine rules are supported when rules exist.

Security support is not one flat claim across every adapter. The
canonical app/web source-sink-sanitizer taxonomy applies to the
general-purpose languages. Solidity is supported as a parser/navigation
adapter and as a smart-contract security pack; its rule taxonomy is
on-chain-specific rather than web-family-specific.

| Language | Sources | Sinks | Lifecycle | Adapter-owned dispatch facts | Inherent limitations |
|---|---|---|---|---|---|
| C | Yes | Yes | Limited | Functions, structs, pointers, out-params, field places | Preprocessor expansion and indirect pointers can be unresolved |
| C++ | Yes | Yes | Limited | Namespaces, methods, constructors, inheritance, aggregates | Uninstantiated templates and runtime polymorphism can be unresolved |
| C# | Yes | Yes | Yes | Namespaces, classes, inheritance, lambdas, async calls | Reflection and `dynamic` dispatch are unresolved without type evidence |
| Dart | Yes | Yes | Limited | Libraries, classes, constructors, methods, futures | Mirrors and generated framework code require emitted source facts |
| Elixir | Yes | Yes | Limited | Modules, qualified calls, pipes, closures, map fields | Runtime macro expansion is not executed |
| Erlang | Yes | Yes | Limited | Modules, functions, message forms, closures | Dynamic atoms and computed `apply` targets can be unresolved |
| Go | Yes | Yes | Limited | Packages, functions, methods, interfaces, tuple returns | Interface dispatch narrows only when concrete type facts exist |
| Java | Yes | Yes | Yes | Packages, classes, constructors, inheritance, lambdas | Reflection and generated bytecode are not executed |
| JavaScript | Yes | Yes | Limited | ES modules, CommonJS, classes, closures, async calls | Computed properties and runtime prototype mutation can be unresolved |
| Kotlin | Yes | Yes | Yes | Packages, classes, inheritance, lambdas, expression bodies | Compiler-plugin DSL expansion is not executed |
| Lua | Yes | Yes | Limited | Functions, closures, tables, dot/colon calls | Runtime metatable dispatch can be unresolved |
| Objective-C | Yes | Yes | Limited | Selectors, receivers, blocks, classes, C bridge calls | Runtime selector construction can be unresolved |
| Perl | Yes | Yes | Limited | Packages, subs, closures, method/arrow calls | Symbol-table mutation and computed dispatch can be unresolved |
| PHP | Yes | Yes | Limited | Namespaces, classes, constructors, closures, includes | Variable functions and computed includes can be unresolved |
| Python | Yes | Yes | Yes | Modules, decorators, classes, closures, async calls | Monkey-patching and highly dynamic attributes can be unresolved |
| Ruby | Yes | Yes | Limited | Modules, classes, blocks, closures, method dispatch | `method_missing` and runtime metaprogramming can be unresolved |
| Rust | Yes | Yes | Yes | Modules, impls, traits, closures, tuples, async calls | Unexpanded procedural macros and trait objects can be unresolved |
| Scala | Yes | Yes | Limited | Packages, objects, classes, inheritance, lambdas | Runtime reflection and compiler-expanded implicits can be unresolved |
| Solidity | Contract globals/params | Smart-contract taxonomy | Yes | Contracts, inheritance, modifiers, external calls | Uses on-chain hazard rules rather than app/web taxonomy |
| Swift | Yes | Yes | Limited | Modules, classes, protocols, closures, async calls | Dynamic Objective-C bridging can be unresolved |
| TypeScript | Yes | Yes | Limited | ES modules, types, classes, closures, async calls | Type erasure and computed runtime properties can be unresolved |
