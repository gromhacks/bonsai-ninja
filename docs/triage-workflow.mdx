# Triage Workflow

<Steps>

1. Read the source, sink, status, severity, and CWE.
2. Follow the `F:` flow from source to sink.
3. Decide whether the tainted value can reach the dangerous argument in the deployed path.
4. Check sanitizer evidence and context.
5. Fix, suppress, or tune the rule.
6. Re-run the same command and compare stable IDs.

</Steps>

## Reading A Finding

Start with the sink rule and `tainted args` line. If the tainted argument is not the dangerous parameter for that API, fix the rule constraint. If the source is too broad, tighten the source rule or run without inferred sources.

```text
FINDING 1 · command-injection · critical  S:979a7231afe45297
  status: unsanitized
  SOURCE python.flask.request_args_get at app.py:29
  SINK   python.cmdi.os_system at executor.py:29
  tainted args: [0] cmd
```

## True Or False Positive

| Question | Evidence of unsafe use | Evidence against unsafe use |
|---|---|---|
| Is the source attacker controlled? | Input crosses the deployment's relevant trust boundary | Proven constant or a value the relevant attacker cannot control |
| Is the sink dangerous in this context? | Shell, query, template, file, external call | Literal safe arg or non-dangerous overload |
| Does the flow preserve the value? | Tainted arg labels line up hop by hop | Wrong field, wrong receiver, impossible branch |
| Is protection proven for this use? | No credited protection, a wrong-context sanitizer, or only a taint transform | Exact lineage has a compatible sanitizer or complete compiler-proven guard |

A matching tag alone does not prove protection: verify the checked value,
guard polarity, execution order, and eventual sink argument. URL encoders,
shell quoting, and other `TAINT TRANSFORM` steps retain attacker control.
Use `--show-sanitized` to review credited paths, and read `status` rather than
inferring safety from the presence of an escaping call. A row's static evidence
still needs deployment-context review; a clean result is not a runtime safety
guarantee. A test or example path is a review-scope decision, not evidence that
the code itself is safe; deliberately vulnerable fixtures can contain real
source-to-sink paths.

## Suppression Syntax

Prefer rule fixes over suppressions. When a project needs local policy, disable
or replace the rule in `<workspace>/.bonsai/rules/` with the same rule ID. Do
not copy this overlay-only suppression pattern into the bundled pack.

```yaml
- id: python.cmdi.os_system
  enabled: false
  disabled_reason:
    code: over-broad
  language: python
  tag: command-injection
  match:
    kind: call
    callee:
      attribute: [os, system]
  description: "Disabled locally because this workspace's wrapper-only use makes the shipped match over-broad."
```

## Finding-ID Semantics

| ID | Meaning | Use |
|---|---|---|
| `S:` | Stable finding ID | Cross-run dedupe and triage tracking. |
| `F:` | Stable flow ID | Re-render a security taint path with `show F:...` or `security taint-analysis --flow`; use `inspect-graph --flow` only for structural `inspect-graph` flow IDs. |
| `G:` | Stable group ID | Re-render a structural group with `show G:...` / `inspect-graph --group`, or a security taint group with `show G:...` / `security taint-analysis --group`. |
| `T:` | Taint propagation record ID | Raw `inspect-graph` taint flow or `dump-taint` propagation; reopen with `show T:...` (add `--taint-source` and the original seeds for `dump-taint` ids). |

## Re-Run

```bash
bonsai-ninja security ./src taint-analysis --format json --all > after.json
bonsai-ninja security ./src taint-analysis --baseline before.json
bonsai-ninja security ./src taint-analysis --flow F:0123456789abcdef
bonsai-ninja show ./src --id F:0123456789abcdef
```

`--baseline <PREV_JSON>` compares the current report with an earlier
`--format json --all` file and labels each finding `new`, `unchanged`, or
`fixed` (text appends a `baseline diff` line; JSON adds `baseline_status` per
row and a top-level `baseline` object). It is render-only and reuses the
current analysis.
