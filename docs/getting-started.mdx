# Getting Started

## Install

### Install with Cargo

```bash
# Requires Rust 1.88 or newer.
cargo install bonsai-ninja --locked
bonsai-ninja --version
```

Cargo compiles the published source for the current host. The package embeds
the same content-addressed default rulepack as the release archives. The first
compiler-backed command for a language may fetch that host's pinned native
Tree-sitter parser bundle into the user cache; later commands reuse the
verified bundle. See [Platform And Architecture Support](platform-support.mdx)
for the supported release targets and offline deployment options.
Re-run the install command with `--force` to replace an older Cargo-installed
release.

### Build from this repository

```bash
cargo build --release --locked -p bonsai-ninja
./target/release/bonsai-ninja --version
```

### Install from source on macOS or Linux

The release binary contains the default security rulepack, so security rules
work from any directory without a companion data path. Native Tree-sitter
parsers use the pinned platform-bundle delivery described below:

```bash
cargo build --release --locked -p bonsai-ninja

PREFIX="${HOME}/.local"
mkdir -p "${PREFIX}/bin"
install -m 755 target/release/bonsai-ninja "${PREFIX}/bin/bonsai-ninja"

"${PREFIX}/bin/bonsai-ninja" --version
```

Add `~/.local/bin` to `PATH` if it is not already present. Security commands
materialize the embedded, content-addressed pack under the operating-system
cache on first use. `--rules-dir <DIR>` or `BONSAI_RULES_DIR` selects an
editable/custom base pack instead.

### Use a tagged release archive

When a tagged release is published, its archives include the readable rulepack
source for inspection and customization even though the binary also embeds
that default. Archives also receive a separate SHA-256 checksum and signed
GitHub/Sigstore provenance. Verify the downloaded archive before extracting it:

```bash
shasum -a 256 -c bonsai-ninja-x86_64-unknown-linux-gnu.tar.gz.sha256
gh attestation verify bonsai-ninja-x86_64-unknown-linux-gnu.tar.gz \
  --repo gromhacks/bonsai-ninja
```

`gh attestation verify` uses the GitHub CLI to verify the artifact digest,
Sigstore signature, source repository, workflow identity, and build commit.
The SHA-256 file is still useful for offline integrity checks; the signed
attestation establishes provenance.

After verification, extract the archive for your operating system and CPU,
then run the binary from its directory:

```bash
tar -xzf bonsai-ninja-x86_64-unknown-linux-gnu.tar.gz
cd bonsai-ninja-x86_64-unknown-linux-gnu
./bonsai-ninja --version
```

On Windows, verify and extract the `.zip` in PowerShell:

```powershell
$archive = "bonsai-ninja-x86_64-pc-windows-msvc.zip"
$expected = (Get-Content "$archive.sha256").Split()[0].ToLower()
$actual = (Get-FileHash $archive -Algorithm SHA256).Hash.ToLower()
if ($actual -ne $expected) { throw "SHA-256 checksum mismatch" }
gh attestation verify $archive --repo gromhacks/bonsai-ninja
Expand-Archive $archive
& ".\bonsai-ninja-x86_64-pc-windows-msvc\bonsai-ninja.exe" --version
```

See [Platform And Architecture Support](platform-support.mdx) for release
targets and source-build requirements.

## Map a workspace

Start with cheap structural facts:

```bash
./target/release/bonsai-ninja index ./src --no-color --no-progress --format json
./target/release/bonsai-ninja tree ./src --max-depth 3 \
  --context 16k --no-color --no-progress
./target/release/bonsai-ninja entrypoints ./src \
  --context 16k --no-color --no-progress
```

Indexing is optional. Run it when you expect several queries:

```bash
# Syntax and declaration warm-up.
./target/release/bonsai-ninja index ./src --no-progress

# Keep saved changes warm while editing.
./target/release/bonsai-ninja index ./src --watch --no-progress
```

Use `index ./src --semantic` only for repeated broad semantic queries. Normal
commands compute their requested exact facts on demand.

## Follow one behavior

Find an anchor, then pivot to compiler facts:

```bash
./target/release/bonsai-ninja search ./src --query verify_token \
  --context 8k --no-color --no-progress
./target/release/bonsai-ninja refs ./src --symbol verify_token \
  --context 8k --no-color --no-progress
./target/release/bonsai-ninja calls ./src --callee verify_token \
  --context 8k --no-color --no-progress
./target/release/bonsai-ninja inspect-graph ./src --query verify_token \
  --context 16k --no-color --no-progress
```

When both endpoints are known, request the exact corridor:

```bash
./target/release/bonsai-ninja inspect-graph ./src \
  --from handle_request --to verify_token \
  --context 16k --no-color --no-progress
```

Use qualified `Owner.member` selectors when short method names collide.

## Run a security scan

Security analysis uses the bundled production profile by default. It selects
remote input, every sink severity, and common non-production path exclusions
from rulepack metadata:

```bash
./target/release/bonsai-ninja security ./src taint-analysis \
  --context 16k \
  --no-color \
  --no-progress
```

For a sink-first review, keep every matched endpoint visible and map exact
source-independent upstream compiler lineage:

```bash
./target/release/bonsai-ninja security ./src sink-analysis \
  --context 16k \
  --no-color \
  --no-progress
```

`upstream_flows` remains present even when no selected security source reaches
the endpoint. Exact selected-source proofs are reported separately under
`security_source_flows`. Default analysis keeps every severity. When a narrower
review is intentional, pass a floor such as `--severity high`; the report header
and JSON summary echo that effective filter.

For a complete machine-readable artifact:

```bash
./target/release/bonsai-ninja security ./src taint-analysis \
  --format json \
  --all \
  --output-path bonsai-findings.json \
  --no-color \
  --no-progress
```

Check `analysis_complete` and `analysis_incomplete_reasons` before treating an
empty result as evidence that no path exists. `--all` removes output paging;
it does not change semantic analysis.

Use SARIF for code-scanning platforms:

```bash
./target/release/bonsai-ninja security ./src taint-analysis \
  --format sarif \
  --all \
  --output-path bonsai.sarif.json \
  --no-color \
  --no-progress
```

Compiler-backed commands exclude adapter-classified minified
JavaScript/TypeScript before parsing by default, so the same source scope is
used by indexing, navigation, callgraphs, security, and export. Add the global
`--minified-js` switch only when bundle internals are intentionally in scope.
Use `--profile all --minified-js` together for an unfiltered security audit,
including local trust, non-production paths, and minified source. `tree` is a
direct filesystem view and still displays those files.

## Read a finding

A security finding includes:

- `S:` stable finding ID;
- source rule and exact source location;
- sink rule and exact sink location;
- `F:` representative taint-path ID;
- `G:` finding-group ID;
- tainted argument and propagation steps;
- sanitizer or taint-transform evidence;
- completeness metadata.

Read the path's `status` together with its evidence. A `TAINT TRANSFORM`
preserves attacker control; URL encoding or shell quoting alone is not a
sanitizer guarantee. Use `--show-sanitized` to inspect credited protections
and follow [Triage Workflow](triage-workflow.mdx) for context checks.

Reopen evidence with:

```bash
./target/release/bonsai-ninja show ./src --id S:<id> \
  --context 16k --no-color --no-progress
./target/release/bonsai-ninja security ./src taint-analysis --flow F:<id> \
  --context 16k --no-color --no-progress
./target/release/bonsai-ninja security ./src taint-analysis --group G:<id> \
  --context 16k --no-color --no-progress
```

`inspect-graph` is rulepack-free. It attaches one bounded compiler evidence
unit (a stable `F:` flow) to every matching callable and expands every raw
taint flow through a match into its full call stack, so the context around a
symbol is visible in one command.

For symbol lookup, start with plain `inspect-graph`, `refs`, or `calls`. Each
`inspect-graph` declaration hit carries the source, signature, imports,
direct resolved callers and callees, and external-call evidence for that
callable; `inspect-graph` rows never recursively enumerate call paths.
If both ends are known, use `inspect-graph --from ... --to ...` for the exact
compressed compiler corridor.
