# bonsai-ninja specification

Multi-language static analysis platform. This document is the top-level
behavioural contract; cross-cutting details live in
[`architecture.mdx`](architecture.mdx),
[`taint-engine-spec.mdx`](taint-engine-spec.mdx),
[`../security-spec.mdx`](../security-spec.mdx), and
[`design-patterns.mdx`](design-patterns.mdx).

## 1. Goals

1. Parse 20 languages: C, C++, C#, Dart, Elixir, Erlang, Go, Java,
   JavaScript, Kotlin, Lua, Objective-C, Perl, PHP, Python, Ruby, Rust,
   Scala, Swift, TypeScript.
2. Produce a step-by-step trace that crosses files and modules.
3. Make the primary output machine-consumable JSON with a stable schema;
   render text / DOT / SARIF on top.
4. Degrade explicitly — every step carries `Precision::{Exact, Narrowed,
   OverApproximate, Unknown}`. Semantic call edges also carry resolver
   stage, evidence, and confidence. Never silently invent precision.
5. Scale incrementally after edits — immutable per-file compiler objects are
   keyed by relative path, adapter, frontend ABI, and SHA-256 source content;
   dependent sidecars add their exact pipeline fingerprints.
6. Be easy to extend with a new language without modifying the engine —
   each adapter implements the trait in `crates/lang_api`; the engine
   never names a language directly.

Tree-sitter is the syntax layer of a compiler pipeline. Adapters own grammar
node kinds, source tokens, declarations, imports, scopes, calls, receivers,
constructors, types, and `FlowEvent` lowering. Shared passes consume the
typed IR; a language-specific syntax fix must not become a language-id branch
or cross-language spelling inventory in the resolver, IDG, taint, security, or
export crates.

External library signatures are rulepack data. An adapter may lower an inline
callback relationship or an explicitly typed callable binding, but it must not
invent the framework's callback parameter types. Compact syntax headers retain
those exact relationships so broad planning and full-body matching apply the
same rulepack typing model without reparsing or guessing. Declared type
identity is case-sensitive; capitalization alone is never type evidence.

Semantic prewarm publishes one atomic compiler-object generation and all broad
phases stream it. Persisted IDG transfer lowers each function once through a
bounded source-weighted worker window, publishes completed segments in
canonical `SegmentId` order, then replays a typed stitch object against the
canonical segment. Caching, parallel completion, or disk spilling must not
create a second semantic frontend, change stable node identity, omit
diagnostics, or cap the fixed point.

## 2. Output schema

### 2.1 `TraceResult` (produced by `trace`)

`crates/trace/src/lib.rs` defines the public schema:

```
TraceResult {
  trace_id, query, summary,
  paths: Vec<PathSummary>,
  steps: Vec<TraceStep>,
  edges: Vec<TraceEdge>,
  states: Vec<StateSnapshot>,
  diagnostics: Vec<TraceDiagnostic>,
  metadata: TraceMetadata,
}
```

`summary.analysis_complete` must be false for any budget truncation or
semantic gap. Budget reasons live in `summary.truncation_reasons`;
non-budget gaps such as unresolved call expansion live in
`summary.analysis_incomplete_reasons`.

`TraceStep` is `{ id, path_id, order, kind, message, function, module, file,
span, code, state_before, state_after, precision, notes }` with
`TraceStepKind` covering EnterFunction, EvalExpr, Assign, BranchSplit, Return,
Throw, and the other typed interpreter steps.

### 2.2 `Finding` (produced by `security taint-analysis`)

`crates/security/src/finding.rs`:

```
Finding {
  finding_id, representative_flow_id, group_id,
  language, severity, precision, status,
  tag, cwe, owasp,
  source: FindingMatch,
  sink: FindingMatch,
  sanitizers_seen: Vec<FindingMatch>,
  taint_transforms_seen: Vec<FindingMatch>,
  analysis_complete, analysis_incomplete_reasons,
  taint_path: Vec<TaintPropagationStep>,
  chain_display: Vec<String>,
  alternate_flows: Vec<AlternateTaintFlow>,
  hops: Vec<FlowFunctionBody>,
  from_test,
}
```

One concrete semantic sink is one finding. `alternate_flows` retains the
other complete source/path/sink-argument/sanitizer/status/precision tuples
without duplicating the finding row. Finding IDs are FNV-1a-64 over the
combined source identities, sink identities, representative group, and
language, formatted as `S:xxxxxxxxxxxxxxxx` and stable across runs.

### 2.3 Browse output (`*Out` types)

Each browse command emits a stable shape:

- `DefOut { name, qualified_name, kind, file, line, column, params }`
- `CallOut { resolution_scope, callee, file, line, column, caller, call_kind }`
- `RefOut { symbol, file, line, column, kind, snippet }`
- `ImportOut { file, module, alias, original_name, is_wildcard, line, local_bindings }`
- `VarOut { name, file, line, column, in_function, writes, source_name }`
- `StringOut { text, category, file, line, column }`
- `ClassOut { name, kind, file, line, method_count, methods }`

Field names are part of the public contract.

### 2.4 SARIF 2.1.0

`security taint-analysis --format sarif` emits SARIF for GitHub code
scanning. See [`../security-spec.mdx`](../security-spec.mdx#output-formats).

## 3. Stability

Public type field names in the SDK and CLI output are stable across
minor versions. Adding a field is a minor change; renaming or removing
one is a breaking change requiring a major version bump.

The `MATCHER_POLICY_FINGERPRINT` and explicit sidecar schema/semantic ABI
versions identify matcher and engine semantics. Source, dependency,
configuration, rulepack, transfer, or ABI mismatches invalidate sidecars
before reuse. The analyzer release/commit fingerprint is producer provenance,
not a replacement for those exact cache inputs.

## 4. Engine standalone contract

The taint engine is a pure function:

```rust
interprocedural_taint(entry_func, entry_sources, config, db) -> InterTaintResult
```

Given an empty `entry_sources`, it produces zero records. The engine
never invents taint without an explicit source. The security layer is
one of many possible drivers; the SDK exposes the engine for use in
custom analyses, language servers, batch review tools, and ad-hoc
tooling.

CLI and SDK consumers drive the engine through
`interprocedural_taint_with_caches`, which reuses `InterTaintCaches` while
running the same IDG closure to its fixed point. There is no scheduler budget,
continuation token, or second interprocedural worklist. The standalone form
documented above and the cache-aware form have the same completeness contract.

## 5. Precision contract

Every fact crossing a layer boundary carries a `Precision`:

- `Exact` — derived without approximation from facts admitted by the modeled
  static semantics; this does not claim that absent runtime/build evidence was
  recovered.
- `Narrowed` — precise within documented static-evidence constraints.
- `OverApproximate` — may include spurious paths.
- `Unknown` — gave up.

`meet(a, b)` returns the worse of the two. Chains take the worst seen.
Public review/security/debug commands render only Exact / Narrowed evidence.
If a requested path would require OverApproximate / Unknown evidence, the
command must omit the broad edge/path and mark the result incomplete with a
reason instead of presenting spurious evidence as complete.

## 6. Determinism

The same workspace + same config produces the same output across:

- Multiple processes (FNV-1a-64 hashes pin finding / flow / group ids).
- Cache reload (sidecar validation re-derives identical results).

Security JSON location fields currently reflect the selected workspace's
filesystem paths, so byte identity and `S:` IDs assume the same canonical
workspace root as well as the same source/config. Native export instead uses
workspace-relative code locations plus one top-level `workspace_root`.

The pinning test is `finding_ids_deterministic_across_runs`.

## 7. Languages

Each language is implemented as an adapter under `crates/lang_<name>`.
Adapters declare their `LanguageCapabilities` (modules, generics, macros,
dynamic dispatch, exceptions, async/await, coroutines, reflection, ffi,
pattern matching) at `Exact` / `Partial` / `Unsupported`. Consumers
degrade gracefully on `Unsupported` constructs.

See [`../COVERAGE_BASELINE.md`](../COVERAGE_BASELINE.md) for the
current matrix.

## 8. Extensibility

- Adding a new language means implementing `LanguageAdapter`, declaring
  syntax capabilities explicitly, lowering all supported compiler facts, and
  passing the cross-language conformance matrices. Size follows the grammar;
  there is no line-count target.
- Adding a new rule means declaring real API semantics plus positive and
  negative examples (see [`../pattern-guide.mdx`](../pattern-guide.mdx)).
- Adding a browse command means building on canonical workspace facts and the
  shared paging/stable-ID surfaces rather than reparsing source.
- Adding a new analysis: implement on top of `bonsai_taint`,
  `bonsai_callgraph`, or `bonsai_abstract_interp`.

The core engine never imports concrete `lang_*` crates; only
`bonsai_adapters` and the SDK do. This keeps language-specific code out
of the analysis core.
