# Analysis roadmap

The roadmap extends one compiler pipeline. New language syntax belongs in its
adapter, new security meaning belongs in rule data, and shared analysis grows
only through language-neutral typed facts and algorithms.

The ordering below is architectural, not a date or staffing promise.

## Current foundation

The shipped engine already provides:

- Tree-sitter frontends for all 20 supported languages;
- adapter-owned declarations, imports, scopes, types, values, calls,
  assignments, branches, callbacks, aggregate places, and `FlowEvent`s;
- compiler-resolved callgraph and receiver/inheritance narrowing;
- field-sensitive intra- and interprocedural flow;
- sparse IDG fixed-point taint closure with recursion convergence;
- clean overwrites, output-argument flow, receiver mutation, tuple returns,
  closure capture, and callback transfer;
- rule-driven sources, sinks, sanitizers, passthroughs, external typing, and
  guard semantics;
- first-party sanitizer-summary inference for compiler-proven function bodies;
- flow-sensitive lifecycle state and must-alias constraints;
- constant, literal-set, range, nullness, and value-shape facts;
- exact completion, precision, provenance, and stable-ID metadata;
- immutable compiler objects and external-memory semantic sidecars for large
  repositories.

The executable coverage sources are
[Taint Coverage Matrix](../TAINT_COVERAGE_MATRIX.md),
[Coverage Baseline](../COVERAGE_BASELINE.md), and
[Adapter Capabilities](adapter-capabilities.mdx). Do not duplicate their
counts in this roadmap.

## Priority 1: frontend evidence completeness

Improve adapter lowering where valid source syntax still lacks a typed fact.
High-value areas are:

- receiver and callable identity through language-specific aliases;
- inheritance, traits, protocols, interfaces, and `super` dispatch;
- expression-bodied and implicit returns;
- callback parameters, closures, and callable values;
- aggregate construction, destructuring, tuple returns, and projected places;
- build-target and module visibility evidence;
- diagnostics for unsupported macro, reflection, FFI, and dynamic-dispatch
  boundaries.

Each change must add a positive fixture, a nearby negative fixture, malformed
source coverage, and the smallest `FlowEvent`/capability assertion that pins
the adapter fact. Shared crates must not learn the source spelling.

## Priority 2: value and guard precision

Expand generic compiler facts that prove when a value is constrained or
rebuilt safely:

- control-dependent allowlists and deny lists;
- path normalization plus containment;
- URL parsing, host/scheme validation, and reconstruction;
- exact character filtering and escaping;
- safe parser configuration state;
- constant-map lookup and finite literal selection;
- prototype-key filtering;
- multi-step first-party sanitizer helpers.

The security layer may assign meaning only through rule-declared semantics.
The compiler proof must identify exact inputs, outputs, branches, mutations,
and return paths. A helper name, variable name, capitalization convention, or
rendered text pattern is never a proof.

## Priority 3: lifecycle and resource correctness

Promote lifecycle audit signals into later-use findings only when the engine
proves the same value and required prior state. Target families include:

- use after free, close, dispose, move, cancel, or release;
- double release and invalid unlock;
- resource or lock loss on exceptional paths;
- iterator/container invalidation;
- transaction state misuse;
- time-of-check/time-of-use pairs.

Work here should extend generic transition/state semantics or adapter-emitted
lifecycle events. API spellings and state policy remain in the rulepack.

## Priority 4: type, alias, and abstract-value precision

Continue narrowing with source-visible evidence:

- control-flow-dominating runtime type tests;
- discriminated unions and exhaustive pattern arms;
- cross-procedural must-alias summaries where identity is provable;
- value ranges, bounded string properties, and finite-set propagation;
- external return/callback typing that retains exact import and shadowing
  proof;
- receiver configuration state across immutable construction and explicit
  mutators.

Ambiguous callable or type identity must fail closed. A new precision feature
must not widen candidate edges as a shortcut.

## Priority 5: exact scale

Performance work must preserve semantic identity. Preferred improvements:

- reject candidates from compact syntax/import headers before body decode;
- stream compiler bodies and graph segments instead of retaining both;
- reuse canonical linkage, callgraph, and IDG query accelerators;
- allocate dense, Bloom, or spill representations only after measured
  relation density crosses the promotion threshold;
- schedule workers from source size and non-reclaimable memory reserves;
- precompute page costs without formatting unrequested pages;
- keep one-shot exports streaming and avoid hidden multi-gigabyte caches.

Forbidden “optimizations” include file limits, depth limits, fixed-point
iteration limits, result caps, guessed edges, and approximate equality that
changes the answer. Run the pinned large-workspace gate for every relevant
change.

## Priority 6: rulepack breadth

Rule coverage can grow independently when the engine already exposes the
required proof. Add a rule only when:

- it represents a real source, sink, sanitizer, lifecycle boundary, or typing
  model;
- package/import/receiver/argument/configuration constraints distinguish the
  intended API from common local lookalikes;
- positive and negative examples cover every discriminating constraint;
- taint-dependent examples replay through the live engine;
- a generic print, log, join, parse, or constructor name is not treated as a
  security boundary by itself.

## Definition of done

An analysis capability is complete only when:

1. the owning adapter or shared typed IR exposes the evidence;
2. shared analysis consumes it without language or provider branches;
3. rules contain all security/provider meaning;
4. positive, negative, malformed, cache, and cross-file tests pass;
5. completeness and precision metadata remain truthful;
6. cold and warm results are identical;
7. memory scheduling changes time or representation only;
8. CLI, SDK, security, and export surfaces agree;
9. documentation and snapshots are updated;
10. the applicable release gates in
    [Release Readiness](../RELEASE_READINESS.md) pass.
