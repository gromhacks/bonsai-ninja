# Adapter Decl-field population

Which **optional** `Decl` struct fields each language adapter
populates. Core taint propagation runs on every supported language, but
semantic receiver dispatch, inheritance, and class-scoped rules depend on
these fields being present. They are not cosmetic: when an adapter fills
the field, the resolver can narrow virtual edges, the taint engine can
credit cross-method writes, and rule matching can avoid receiver-name
heuristics.

## TL;DR

- Every adapter populates the **required** `Decl` fields (name, kind,
  span, params, flow events). That's what makes taint analysis work.
- The table below tracks **eight optional** fields. Most adapters
  fill some of them and leave the rest unpopulated.
- A `—` cell means *the language has the construct, but the adapter
  doesn't yet populate the field*. Treat it as a real precision backlog
  item.
- An `n/a` cell means *the language has no equivalent construct*
  (e.g. Erlang has no class hierarchy → no `bases`). Filling it
  wouldn't make sense.
- A `✓` means the adapter populates the field for typical cases.

This is the **adapter-side** view ("does the adapter wire up these
fields?"). The complementary [**engine-side**
view](../COVERAGE_BASELINE.md) ("what does the engine model?") lives
in `COVERAGE_BASELINE.md`.

> **Reading this alongside [`TAINT_COVERAGE_MATRIX.md`](../TAINT_COVERAGE_MATRIX.md)?**
> The taint matrix shows every applicable scenario × language cell as
> `pass` — that's behavioural truth from real engine tests. A `—` in
> the table below means receiver/class-specific rules may lose precision
> for that language until the adapter emits the missing semantic fact.

## What each field powers

| Field | What it enables | If empty |
|---|---|---|
| `Visibility` | Resolver filters out private callees from foreign modules. | All decls treated as `Public` — wider candidate set, more `OverApproximate` edges. |
| `type_aliases` | Resolver matches `MyTypedef` to the underlying class for receiver dispatch. | Calls through typedefs may not resolve to receiver-typed rules. |
| `receiver_types` | Shared DB/index pass copies semantic receiver type facts onto `FlowEvent::Call` so callgraph, taint, rules, inspect, browse, and export consume the same evidence. | `[Type, method]` rules require another semantic fact or do not match. |
| `bases` | Cross-class virtual dispatch narrows when the receiver type is known. | Parent/interface rules and inherited dispatch may not match. |
| `receiver_field_writes` | G3 cross-method field-taint inheritance: `def m1(x): self.f = x` → `def m2(): use(self.f)` propagates taint. | Field-aliased flows aren't crossed; intra-method propagation still works. |
| `has_implicit_returns` | Return summaries can use terminal-tail evidence only for real expression-return body forms. | Terminal assignments are never treated as returns; expression-bodied helpers may need explicit `Return` events. |
| `param_annotations` | Synthetic-source inference: `@route("/api")` on a Flask handler treats the params as remote sources without an explicit YAML rule. | Inferred sources need explicit rules instead. |
| `export_aliases` | CommonJS resolver credits `module.exports = X` to the module's public surface. | `require()` consumers don't see the assignments. |
| `super_dispatch` | `super.foo()` resolves precisely to the parent class's `foo`. | The edge remains unresolved/incomplete unless another semantic fact proves it; public analysis never widens to name-only dispatch. |

These fields do not gate basic taint propagation, but they do gate
semantic receiver/class precision. `has_implicit_returns` gates return
summary precision. Do not replace these fields with receiver-name,
language-name, or span-containment workarounds.

## What the cells mean for users

If you're triaging a finding and wondering whether the adapter's
gaps affect it:

- **`Visibility = —`:** the engine includes private decls in the
  candidate set across modules. Findings might cite a callee that
  another module shouldn't be able to reach. Real risk for code
  review; not a soundness issue (over-reporting, not under-reporting).
- **`bases = —` / `super_dispatch = —`:** virtual dispatch on this
  language's class hierarchy may not have enough type evidence to emit
  a complete semantic edge. Public analysis must report that gap as
  incomplete instead of emitting wider candidate sets as findings.
  `OverApproximate` remains an internal diagnostic precision class and
  is rejected by user-facing flow/security commands.
- **`receiver_field_writes = —`:** taint that flows through
  `self.field = x` and is later read by another method on the same
  object won't be tracked. Cross-method same-class flows degrade —
  intra-method flows still work.
- **`param_annotations = —`:** synthetic per-route entry-point
  sources (Flask `@route`, FastAPI handlers, Spring `@RequestBody`)
  are only inferred for languages where this is populated. Other
  languages need explicit source rules in YAML.

## Backlog candidates

Visible from the matrix above:

- **`receiver_field_writes` is populated for Go, Lua, and Perl via
  adapter-specific receiver shapes.** Go uses explicit receiver
  parameters (`func (h *Handler) Set(...)`), Lua factory constructors
  lower `self.field = x`, and Perl `bless { field => $x }` constructors
  lower hash keys into receiver-field writes.
- **`param_annotations` remains narrow where the language-specific
  binder shape is not normalized yet.** Java, Kotlin, C#, Python,
  Dart, Objective-C, PHP, Rust, Scala, Swift, and TypeScript emit
  adapter-visible parameter annotation facts for the common grammar
  shapes; Ruby is partial. Solidity modifiers remain candidates for
  route/source inference without per-language YAML.
- **`super_dispatch` is partial in several adapters that have
  inheritance.** JavaScript/TypeScript, Java/Kotlin/PHP/Python/Ruby/Rust,
  C#/Dart, and the tested `super`/`parent`/`base` receiver shapes have full
  support today; C++/ObjC/Scala/Swift remain partial.
- **JavaScript / TypeScript receiver types are now populated for common
  class shapes, but dynamic prototype mutation remains a precision gap.**

## How this matrix is gated

The grep audit `scripts/audit-adapter-capabilities.sh` writes counts
to `.snapshots/ADAPTER_CAPABILITIES.snapshot`. The CI gate
(`hardening-checks.yml::capabilities`) runs `--check` which fails on
drift between the script's live output and the snapshot.

The behavioral conformance gate
`cargo test -p bonsai_conformance capability_matrix_report` probes every
registered adapter and writes generated docs/data to
`build/capability-matrix.md` and `build/capability-matrix.json`. Those
generated files are the machine-readable view; the table above is the
review-oriented summary. `bonsai-ninja diagnostics <workspace>` and
`Project::diagnostics_report()` expose the same registered adapter
capability declarations that the engine consults.

```sh
# detect drift
scripts/audit-adapter-capabilities.sh --check

# regenerate the snapshot after intentional adapter changes
scripts/audit-adapter-capabilities.sh > .snapshots/ADAPTER_CAPABILITIES.snapshot
```

If you change an adapter to populate a new `Decl` field, regenerate the
snapshot, run the conformance report, and update the review table cell.

## `LanguageCapabilities` per-adapter syntax facts

In addition to the `Decl`-field population matrix above, each adapter
declares the exact syntax/linkage facts that shared compiler passes may
consume. There is no cross-language token fallback: an empty slice means the
language does not expose that form.

| Field | Empty/default meaning |
|---|---|
| `module_export_aliases` | no receiver-shaped module export aliases |
| `module_default_export_names` | no callable default-export declaration name |
| `module_path_syntax` | no rooted qualified-name prefixes |
| `universal_type_names` | no type spelling is treated as universally broad |
| `constructor_method_names` | constructors are class-named, grammar-node-only, or unsupported |
| `super_receiver_tokens` | no supertype receiver token |
| `implicit_receiver_tokens` | no implicit instance/class receiver token |
| `field_places_complete` | sink-oriented builds must not assume every property/projection is represented |
| `bare_call_constructor_syntax` | a bare call cannot be classified as construction from exact class identity |
| `same_directory_unqualified_calls` | sibling files require explicit module/import evidence |
| `build_target_linkage` | native build-target membership does not narrow global calls |
| `callable_declaration_family` | repeated same-named declarations are not one compiler-proven callable family |
| `quoted_callable_literals` | quoted literals are ordinary strings, not callable references |
| `call_text_prefilter` | candidate-only text prefilter is disabled |
| `module_resolution_extensions` | extensionless relative imports have no adapter-declared source suffixes |
| `workspace_manifest_context_extensions` | no extra non-source template suffix shares dependency-manifest context |

Use `bonsai_lang_api::NO_CONSTRUCTOR_METHOD_NAMES` when an explicit empty
constructor inventory makes the adapter declaration clearer. It is an empty
slice, not a sentinel that activates fallback behavior.

Engine consumers prefer the adapter-aware accessor:

```rust
let names = db
    .adapter_for(file)
    .map(|a| a.capabilities().effective_constructor_method_names())
    .unwrap_or(&[]);
```

The same `effective_*()` shape exists for `super_receiver_tokens` and
`implicit_receiver_tokens`; those names remain for API compatibility and
return only the adapter's declared values. Code without adapter context uses
the conservative empty behavior.

`field_places_complete` and the boolean/linkage declarations are equally
strict: false/empty disables an optimization or leaves a candidate unresolved;
it never activates a shared heuristic. `call_text_prefilter` can only reject
files that provably lack a supported call grammar shape. Final call facts
always come from the adapter AST.
