# Design patterns

The invariants every contributor should know. Each one exists because we
got burned by the alternative — these are guarantees, not preferences.

If you're reading this for the first time, skim the section headings and
come back to a section when something forces you to.

## 1. Resolve names by structure, not by string

Name resolution always goes through `bonsai_resolve::resolve_callable_with_context`
with a real `ResolveContext`: caller file, caller module, optional receiver
type, optional alias map. The resolver then walks every decl with that name
and applies `visibility_allows` before returning candidates.

Callable values are normalised through
`bonsai_common::callable_reference_variants` so that `&fn/1`, `fun fn/1`,
`\&fn`, PHP string callables, Ruby `method(:fn)`, and qualified tails all
collapse to the same bare callable before lookup.

What this buys you: two unrelated codebases can both declare `static fn
error(…)` without colliding, because each is `Visibility::Private` and the
resolver filters by file. What it forbids: bare `find_by_name(name)` lookups
above the resolver, ad-hoc matching languages, treating a function-name
string match as a call.

For global-namespace languages with translation-unit or shared package
linkage, same-directory unqualified calls are semantic only when the
`ResolveContext` includes the workspace file-path lookup and the caller's
adapter declares `same_directory_unqualified_calls`. This lets native/shared
package helpers resolve without teaching the resolver any language names,
while file-module languages still require imports or aliases.

The receiver-callback shorthand is intentionally narrower than method
calls. `cb.call(x)` / `cb.run(x)` only dispatches when `cb` resolves to a
callable value. Constructed objects (`repo = Repository(x); repo.run()`) go
through receiver-type semantics, not callable resolution. Don't add results
of constructor-shaped calls to the callable binding map.

### 1a. Alias rewrites are constrained by the alias's target module

When `resolve_callable_with_context` and `resolve_class` rewrite a name
through `ctx.alias_map` (e.g. `cp.exec` →
`child_process.exec` for `const cp = require("child_process")`,
`pipeline::orchestrate` → `pipeline.orchestrate` for Rust `mod pipeline;`),
the rewrite produces both a rewritten name and the alias's target
module identity. The exact-rewrite lookup trusts the alias map. The
*bare-name fallback* (the `collect(tail)` retry that exists because
many adapters index decls only by leaf identifier) is filtered by
`module_target_matches_decl_module_path` — a candidate is accepted
only when its `Decl.module_path` suffix-matches the alias target's
dotted segments.

This is the resolver's defense against the "stitch together unrelated
workspace functions" failure mode: without the filter, calling
`Envelope::method` on a type-only Rust import would happily return
any `method()` decl elsewhere in the workspace. With the filter, the
rewrite produces no candidates because no workspace decl named
`method` lives in module `Envelope` — exactly the right answer.

The filter splits the alias target on `.`, `/`, `\`, with `::`
pre-collapsed to `.`, so Java `com.example.Utils`, Dart
`storage.dart`, PHP `App\Util`, and Rust `pipeline::orchestrate` all
decompose correctly. A trailing target segment that doesn't appear
in the decl's module_path is dropped before retrying — handles the
file-extension trailers (Dart) and class-name trailers (Java
`com.example.Utils` vs decl module `com.example`, since the class
name lives in `decl.name`/`decl.parent`, not the module_path)
uniformly without a hardcoded extension allow-list.

## 2. Empty seed produces no propagation

Given `(entry_func, empty_seed, config, db)`, the engine produces zero
records. Every taint introduction goes through the `entry_sources: TokenSet`
parameter. The engine never invents taint from heuristics or implicit-source
patterns.

Source rules and source-returning helpers are translated into concrete IDG
seed nodes by the security layer. The engine does not keep a helper-name
inventory or infer a tainted return from a function name.

Source seeding is identity-strict. A matched source `os.getenv` may seed
`os.getenv` and the tail `getenv`, but never the receiver `os`. A matched
container source `req.query` doesn't seed `req.user` or the whole `req`.
Receiver and sibling substring matches are not proof.

Read-source seeding may add `param.*` descendants when the matched source
is structurally read through a qualified container access, and parameter
source rules may explicitly seed `param.*`. Ordinary call sources don't
get wildcard semantics.

## 3. No text fallbacks for taint introduction

Identifier tokens used in taint state come from adapter-emitted
`source_names`, never from text-walking arbitrary expression strings.

The adapter kit walks tree-sitter expression children and emits only
value-bearing identifier/place nodes. It does not recover taint operands by
tokenizing rendered expressions. The engine's `arg_text_is_tainted` and
`rhs_operand_is_tainted` also short-circuit `false` on `is_quoted_literal`
before any other check.

This matters because a string literal like `'.category == "electronics"'`
must never produce identifier tokens that pollute state. An earlier version
walked through string literals and every seed name that happened to appear
inside a comment string produced spurious flows.

Value-free type/size operators get the same treatment. `sizeof(c)`,
`alignof(T)`, `typeof(x)`, `nameof(x)` mention identifiers but don't read
their runtime values. The engine strips those operands so
`sizeof(c) * cap` only taints when `cap` is tainted.

String interpolation taint comes from adapter-emitted expression operands,
not engine text parsing. A template/f-string argument should carry the
interpolated variable in `source_names`; literal text stays inert.

## 4. Public analysis is semantic-only

Every fact crossing an analysis boundary carries a `Precision` from the lattice
`Exact < Narrowed < OverApproximate < Unknown`, but public analysis evidence is
semantic-only:

- Direct structural facts and fully resolved edges → Exact.
- Edges narrowed by aliases, receiver types, module paths, build targets, or
  declared virtual dispatch semantics → Narrowed.
- Multiple candidates are allowed only when the language facts explain that set
  semantically, such as typed virtual dispatch over the known receiver family
  or same-scope overloads. If declared argument/parameter types identify one
  overload, dispatch must narrow to that candidate instead of flowing through
  siblings.
- Unresolved, dynamic, budget-truncated, or contextless matches are not evidence.
  They must be omitted from semantic results and surfaced through explicit
  incompleteness/debug metadata instead of being widened into findings.
- `meet(a, b)` returns the worse semantic precision across a proven chain; if a
  chain would require `OverApproximate` or `Unknown`, the public command must not
  report it as a finding or flow.

Findings and flow exports render `precision` only for proven semantic evidence
(`exact` / `narrowed`). Diagnostic broad classes may exist internally for cache
round-trips or debugging, but they are not acceptable as user-facing analysis
results.

## 5. Content-addressed caching

Sidecar caches are keyed on content hashes plus a policy fingerprint, never
on volatile IDs. Per-file caches use `(FileId, version)`; per-function
caches use `(FuncId, file_version)`; cross-process caches use file content
hash plus `MATCHER_POLICY_FINGERPRINT`.

Bumping the policy fingerprint is required when you change resolver
narrowing, engine semantics (the various `_is_tainted` paths,
`apply_unresolved_call_side_effects`, `try_body_throws_tainted`), adapter
fact shape, or matcher policy.

## 6. Monotonic invalidation

Edits invalidate; we never compact or reuse symbol slots. When a file is
removed:

1. The VFS bumps `version`.
2. `AnalyzerDb` evicts per-file caches.
3. `GlobalIndex::remove_file` tombstones every `SymbolId` — the slot is
   never reused.
4. Cached structures referencing tombstoned IDs resolve to `None`, not to
   whatever decl now occupies the same index after a re-insert.

`SymbolId`s are stable across the workspace's lifetime. Code holding stale
IDs gets `None` lookups, not silently wrong data.

## 7. One source of truth for imports

`AnalyzerDb::imports_for(file)` is the only path that produces import
facts. It consults the adapter's `extract_imports` first; on absence it
falls back to a generic syntax extractor. The matcher, the dependency
inventory, and the resolver's alias map all see the same shape.

Don't parse imports ad-hoc inside consumer crates.

## 8. Field-sensitive writes and reads, carrier-aware arg passing

Per-field taint precision is split across four engine functions, each with
a tightly-scoped contract:

- **Write side** (`insert_target_taint`): a qualified write `obj.value =
  tainted` writes only `obj.value` into state. The bare carrier `obj` is
  not promoted.
- **Read side** (`arg_text_is_tainted`): a qualified read `obj.safe`
  matches only an explicit qualified seed. A bare tainted carrier doesn't
  poison every field.
- **Carrier argument passing**: `process(obj)` matches any qualified seed
  sharing the same base via `state_qualified_token_matches_text`. This
  preserves whole-object propagation when a tainted field is passed
  through its carrier.
- **Strict RHS** (`rhs_operand_is_tainted`): assignment RHS uses a
  stricter check that doesn't promote bare-name reads to qualified-seed
  matches. `out = data['other']` doesn't inherit `data.value`'s taint.

Named constructor/object fields seed exact fields. `env = Envelope({cmd:
raw, kind: K})` taints `env.cmd` but not `env.kind` or `env.*`. Positional
constructors without named-field facts may still carry descendant-container
taint when a tainted argument flows into a resolved type-like constructor.

## 9. Path-sensitive branch merge via per-arm cloning

`walk_events_for_propagation` clones state for each branch arm, walks both
arms independently, and unions post-states at the merge. The clone-walk-
union pattern keeps the engine path-sensitive without enumerating paths.

Match/switch arms get the same treatment. Adapters whose grammar emits a
flat `Branch` with every arm concatenated into `then_events` collect arm
spans and pass them through `split_match_arms_in_branch_events`, which
reshapes the flat event list into a right-leaning chain of nested
branches.

When the language has typed catch arms, the engine narrows by type:
`catch (IOException e)` doesn't seed when the body throws a
`RuntimeException`, unless the catch type is an absolute root
(`Exception`, `Throwable`, `Error`, `System.Exception`, `Object`) — those
catch anything by spec and seed conservatively.

## 10. Async / spawn isolation

Detached futures don't poison the caller's continuation. When an adapter
identifies a spawn body (Rust `tokio::spawn`, `std::thread::spawn`, etc.),
the body events are wrapped in `FlowEvent::Defer` so the engine treats
them as scope-local. The caller's post-spawn state continues from the
pre-spawn state without absorbing whatever happened inside the body.

## 11. Reflection and dynamic dispatch rewrites

Where a literal-string call can be statically resolved, the adapter
rewrites it to a direct call before the engine runs. Python
`getattr(obj, "method")` and Java
`Class.forName("X").getMethod("Y").invoke(...)` both lower to the
equivalent direct method call so the resolver narrows them like any other
dispatch.

Truly dynamic shapes (computed string arguments, runtime lookup tables)
remain unresolved until an adapter or summary model can prove the target
semantically. The engine must not fan those shapes out into workspace-wide
candidate sets or report them as semantic findings.

## 12. Adapter responsibility versus engine responsibility

The dividing line: language-specific shapes go in adapters; cross-language
analysis goes in the engine.

If a fact is reasoning about *what the source did syntactically* — `throw
new IOException(...)` exposes the type; `tokio::spawn` opens a detached
scope; `module_function :foo` exposes the surface — that's an adapter
post-process.

If a fact is reasoning about *what the engine should do given the
adapter's facts* — should `IOException` taint propagate to a `catch
(Exception e)` arm, should a `Defer` body block continuation taint — that's
the engine.

When in doubt, push the work to the adapter. Engine code should look the
same regardless of the source language.

### 12a. Source syntax belongs to the active adapter

The 21 concrete adapters own Tree-sitter grammar nodes, constructor forms,
receiver tokens, module roots, imports, exports, and broad type spellings.
Shared compiler passes consume `Decl`, `FlowEvent`, `ImportSpec`, `Place`, and
`LanguageCapabilities`; they do not select behavior by language id or use a
union of source-language keywords as semantic proof.

An empty capability means the syntax does not exist. The retained
`effective_*` names are API compatibility shims, not fallback inventories:

```rust
LanguageCapabilities::effective_constructor_method_names()
LanguageCapabilities::effective_super_receiver_tokens()
LanguageCapabilities::effective_implicit_receiver_tokens()
```

Shared textual helpers own no union of source tokens. They may identify the
last top-level identifier segment or remove leading punctuation from a fact
the adapter already classified as a name. Those vocabulary-free operations
are candidate lookup only; symbol identity still goes through the contextual
resolver.

Adapter capabilities carry the source syntax that a shared pass actually
needs:

- `LanguageCapabilities::module_path_syntax` declares rooted qualified-name
  prefixes;
- `LanguageCapabilities::callable_reference_syntax` declares callable-value
  prefixes, numeric arity notation, an optional symbol wrapper, and trailing
  invocation punctuation;
- `quoted_callable_literals` separately opts into quoted callable values.

An adapter-emitted parameter or assignment supplies its own concrete spelling
to token compatibility lookup. Shared taint does not manufacture sigiled
variants from a cross-language list.

New source syntax belongs in its adapter's `GrammarHandler`, AST post-pass,
or capability declaration. Emit a structural fact (`CallKind::Constructor`,
`FlowEvent::Return`, a type alias, or a `Place`) and match that fact downstream.

## 13. Workspace-cached facts, never repeated query-time graph walks

Queries validate reusable facts first. A cache miss can build the exact
requested graph once, but subsequent consumers share that result instead of
repeating the same workspace walk. Every workspace cache follows the same
shape:

1. **Lazy-or-eager build** — the cache holds an
   `Option<Arc<...>>` (or per-key map). `Workspace::open_with_options`
   prewarms it for the canonical "index now, query many times"
   case; `query_only` callers skip the prewarm and let the first
   query lazy-build.
2. **Sidecar persistence** — long-lived caches (`DataFlowCache`,
   `ValueFlowCache`, `TaintGraphIndex`) stream-write to
   the workspace's canonical-path-keyed OS cache as
   `<cache>/<name>.v<version>.factstore` via
   `bonsai_factstore::FactStoreWriter` with atomic-rename +
   `MATCHER_POLICY_FINGERPRINT` validation. Streaming keeps peak
   memory bounded by in-flight payload, not by the total cache.
3. **`parking_lot` interior mutability** — `RwLock<Inner>` (for
   per-key maps) or `RwLock<Option<Arc<T>>>` (for singletons).
   Probe with a read lock; upgrade to write only on miss; check
   the slot again under the write lock so two racers don't both
   commit a value.
4. **Invalidate on edit** — every cache exposes `clear()` (or
   `invalidate_file(file)` for per-file granularity), and
   `Workspace::ingest_dir` calls every one when a file edit lands.

Concrete wiring:

| Cache | File | Build trigger | Invalidation |
|-------|------|----------------|--------------|
| `CompiledFileObject` generation | `crates/db/src/compiler_object.rs` | first `index --semantic` worker; lazy one-file miss | SHA-256/path/adapter/ABI per object; atomic generation replacement |
| compiler linkage | `crates/workspace/src/linkage_sidecar.rs` | semantic linkage worker | complete generation/source/dependency/pipeline identity |
| workspace IDG + query accelerator | `crates/idg/src/workspace.rs`, `crates/idg/src/service.rs` | semantic IDG worker; exact query misses may publish the canonical graph without claiming semantic prewarm | complete source/dependency/transfer pipeline identity plus independently validated accelerator ABI |
| `DataFlowCache` | `crates/workspace/src/dataflow.rs` | `prewarm_all` | per-FuncId via dependency files |
| `ValueFlowCache` | `crates/workspace/src/value_flow.rs` | lazy `graph_for_with_caches`; explicit compatibility prewarm only | clear |
| `FlowIdCache` | `crates/workspace/src/flow_ids.rs` | `prewarm_all` | clear |
| `TaintGraphIndex` | `crates/workspace/src/taint_index.rs` | lazy on first `taint-analysis` | clear |
| `ClassMemberIndex` | `crates/workspace/src/class_index.rs` | lazy | exact `GlobalIndex` snapshot identity |
| `EnclosingIndex` | `crates/workspace/src/enclosing_index.rs` | lazy per file | exact `GlobalIndex` snapshot identity; all files reset together |
| `DeclNameIndex` | `crates/workspace/src/decl_name_index.rs` | lazy | exact `GlobalIndex` snapshot identity |
| `cached_resolved_call_graph` | `crates/workspace/src/lib.rs` | lazy | clear |
| `inter_taint_caches` | `crates/workspace/src/lib.rs` | per-key lazy | clear |

Compiler-object generations are different from ordinary memoization. A
generation is immutable and atomically replaced, while individual unchanged
objects remain reusable from a stale generation after another file changes.
Never publish a partial/scoped generation under the full workspace path, and
never accept an object from path or a fast hash alone.

### 13a. Watch out for `parking_lot` read-then-write hazards

`parking_lot::RwLock` is non-reentrant. Same-thread read→write
deadlocks. The hazard surface is Rust's temporary-lifetime rules:

```rust
// WRONG — the RwLockReadGuard from `.read()` lives across both
// branches of the if-let, so the `else` branch's `.write()`
// deadlocks against this thread's still-held read lock.
if let Some(hit) = exact_graphs.read().get(&key).cloned() {
    return hit;
} else {
    let mut write = exact_graphs.write();
    write.insert(key, computed);
}
```

The fix: end the read-lock temporary at a `;` before the write
upgrade.

```rust
let cached = exact_graphs.read().get(&key).cloned();
if let Some(hit) = cached {
    return hit;
}
let mut write = exact_graphs.write();
write.entry(key).or_insert(computed).clone()
```

The workspace cache helpers follow this shape. New cache code should too.

## 14. Engine entry points are CONTEXTLESS_LOOKUP_JUSTIFICATION marked

Every call to `GlobalIndex::find_by_name` outside the resolver
itself must carry a `// CONTEXTLESS_LOOKUP_JUSTIFICATION:`
comment immediately preceding the call, explaining why a
contextless lookup is acceptable at that site. The conformance
test `engine_resolves_via_context_not_bare_name`
(`crates/conformance/tests/architecture_invariants.rs`)
enforces this.

The justification typically takes one of three shapes:

- **Resolver primitive itself** — `resolve_callable_with_context`
  and `resolve_class_with_context` are the canonical narrow
  resolvers; their `find_by_name` calls feed the immediate
  `visibility_allows` + receiver-type filter.
- **Display-only legacy paths** — `bonsai_resolve::resolve_callable`
  is `#[doc(hidden)]` and consumed by browse output / CLI
  trace-source resolution where cross-context candidate
  enumeration is acceptable.
- **Diagnostic-only compatibility paths** — legacy or debug-only code
  may parse broad precision labels, but public analysis commands must
  filter them out or report explicit incompleteness.

A site that doesn't fit one of these shapes is almost certainly
a bug — replace it with `resolve_callable_with_context`.
